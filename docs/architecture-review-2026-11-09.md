**性质**：只读审查，未改任何代码。

## 一、总体判断

> **这是一套「local-first 复制同步 + 瘦云函数」的模块化单体。对当前阶段（小团队、单产品、教学机构场景）是正确选择，不需要微服务化。真正的架构风险不在分层，在「全量复制模型」的长期演进。**

### 分层现状（C4 组件视图，文字版）

```
┌─ 页面层（21 页，全在主包）──────────────────────────┐
│  record / batch / mgr / mine / orgid / …            │
└──────────────┬──────────────────────────────────────┘
               │ 只依赖门面，无页面间 require，无反向依赖 ✔
┌──────────────▼──────────────────────────────────────┐
│ utils/api.js / sync.js / media.js …（应用服务）      │
└──────────────┬──────────────────────────────────────┘
┌──────────────▼──────────────────────────────────────┐
│ utils/db/*（领域层：6162 行，按聚合拆 27 个文件）    │
│  students / records / classes / org / identity …    │
│  permissions.js（双层规则，已有前后端一致性守卫）    │
└──────────────┬──────────────────────────────────────┘
               │ 本地分片存储（storage.js）+ LWW 同步（syncmerge.js）
┌──────────────▼──────────────────────────────────────┐
│ 云函数（8 个）：syncv2 / admin / aiEval / backup …   │
└─────────────────────────────────────────────────────┘
```

### 做得好的（先说优点，这些别动）

| # | 实践 | 评价 |
|---|---|---|
| 1 | **分层纪律** | 页面 → 门面 → 领域层，零反向依赖、零页面间 require。实测 grep 干净。 |
| 2 | **领域按聚合拆文件** | `utils/db` 27 个文件各管一个聚合，头部注释全在解释「为什么」而不是「是什么」。 |
| 3 | **权限双层 + 一致性守卫测试** | 前端 `permissions.js` 与 syncv2 白名单由测试逐条比对（1148 落地）。规则漂移会红，这是少见的强实践。 |
| 4 | **软删 + 回收站 + 体检** | `trash.js` + `audit.js`（能修的自动修、不能修的只报告）。误删有退路。 |
| 5 | **测试形态** | 50 套件：行为级（mock 云函数真跑 pull/push）+ 源码守卫（钉结构防回退）混合。 |
| 6 | **迁移路径显性化** | `server/` 自建方案头部注释写明「未被调用 + 上线前三件事」。决策上下文留在代码里。 |

## 二、架构级风险（按严重度排序）

### A1【最高】全量复制模型没有「增长刹车」

**现状**：老师端 pull 仍是全机构复制（家长端 1148 已收窄到自家孩子）。本地库 = 机构全量 × 全部历史。

**为什么是架构问题而不是性能问题**：wx storage 上限 10MB（分片机制做得不错），但「一个老师手机里装着全机构所有学生的全部历史」这个模型本身不随用户数缩放。几百学生 × 每周多条记录 × 照片 fileID，一年量级就可预估。

**建议（不急做，先立触发条件）**：
- 触发线：本地库 > 6MB 或单机构 records > 3000 条时启动；
- 方案：老师端从「全机构复制」改「按班级订阅」（pull where 加 clsIds ∈ 我的班级），改动集中在 syncv2 的 where 构造，客户端同步层已支持按集合拉，不需要重写。

### A2【高】LWW 冲突 = 静默丢失，且无冲突审计

**现状**：`syncmerge.js` 明确注释 LWW（比 updatedAt，后写胜）。单人操作没问题。

**风险场景**：同班两个老师同时编辑同一条记录 → 后推的覆盖先推的，**无提示、无副本、无痕迹**。多老师同班是这个产品的真实形态（负责人+管理员的「全机构可见」也在推这个场景）。

**建议**：低成本止血——冲突发生时（LWW 判负但内容不同）把败者副本自动丢进**已有的回收站**（`trash.js` 白捡的基础设施），加一条审计。不做交互式合并（教学场景不值得上 CRDT）。

### A3【中】云函数目录隔离 → 共享代码只能靠复制

**现状**：每个云函数是独立部署单元，`admin/lib.js`、`backup/lib.js` 各一份；`callGLM` 40 行重复（M-3，两轮审查都挂着未修）。

**取舍**：这是微信云开发的部署模型决定的，不是设计失误。但复制要有纪律。

**建议**：把「两份必须一致」的代码升级为守卫（`verify_server_guard.js` 已有先例：require 两侧逐条比对）。callGLM 去重可等 M-3 一起做，但**新写云函数时禁止再手工复制共享段**。

### A4【中】21 页全在主包，无分包

**现状**：主包 1367KB / 66.8%。还健康。

**建议**：`batch / tpls / import / trash / storage / terms` 六个低频页是分包天然候选（合计应能减 15-25%）。**触发线：主包到 75%（1536KB）时动手**，现在不用。

### A5【中】遗留物没有「废弃日历」

| 遗留物 | 体积/状态 | 留着的理由 | 建议处置 |
|---|---|---|---|
| `cloudfunctions/sync/`（旧版 87 行） | 无任何调用方 | 迁移期兼容 | 已过两个大版本，可删（先查后台函数列表确认无流量） |
| `server/`（自建 Express 方案） | 未接线 | 迁移路径参考 | 保留但写明「冻结」，挂路线图 |
| `utils/demo-data.js` | 2369 行进主包 | 演示模式 | 挪分包或按需注入（与 A4 一起做） |
| `.workbuddy/_plat*.js` | 4 份草稿约 3.4MB | QA 会话残留 | 未被 git 跟踪、已被 packOptions 忽略，可清理 |

**架构含义**：每件遗留物都合理，但没有任何机制记得「哪天该删」。建议路线图加一节「冻结清单」，每项写复查日期。

### A6【中】重大决策没有 ADR 沉淀

项目至少有六个重大架构决策，全部散在代码注释里：local-first 存储、LWW、软删+回收站、权限双层、自建 server 备选、多机构模型。注释会跟着代码漂移，「为什么这么定」的上下文没人集中保存。

**建议**：建 `docs/adr/`，先追认五篇（每篇半页）：
1. ADR-001 本地优先 + 云同步（而非直连云数据库）
2. ADR-002 LWW 冲突策略
3. ADR-003 软删与回收站
4. ADR-004 权限双层 + 守卫测试（而不是权限下沉复制）
5. ADR-005 多机构（orgId 全局作用域 + 工牌成员制）

### A7【低】单环境 = 无 staging

云函数改动直接部署到唯一生产环境，真机验证全靠体验版（已用到 1148）。无真实用户前成本为零；**拉新用户前**建议开第二个云环境做 staging，`npm run cloud` 加 env 参数即可。

## 三、演进路线（分阶段，不推倒）

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 现在（<500 用户） | — | 修 M-2/M-3（已挂账）；写 5 篇 ADR；清理 A5 遗留物 |
| 增长期（500–5000） | 本地库 > 6MB 或 records > 3000/机构 | A1 按班级订阅；A2 冲突败者入回收站；A4 分包 |
| 平台期（>5000 或多角色扩展） | 家长端读延迟成投诉 | 评估 CQRS 读模型（家长端专用只读接口）；共享代码构建分发 |

**明确不建议做的**：微服务化（团队规模撑不住）、CRDT/操作变换（场景不值得）、把 server/ 自建方案激活（云开发够用且有 fallback）。

---

## 四、一句话结论

> 分层和纪律是超出这个体位平均水平的；唯一需要提前布局的是「复制模型的增长刹车」（A1）和「冲突静默丢失」（A2）——都不急，但触发线现在就该写进路线图。
