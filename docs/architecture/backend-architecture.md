> 编写：后端架构师 · 2026-11-05

## 0. 结论先行（TL;DR）

现在的后端**在"每天几十条记录、一两家机构"的量级上是可靠且正确的**——local-first、软删可逆、三层备份这些设计比同规模产品扎实。真正的风险不在"会不会挂"，而在**三处结构性缺口**：

| 缺口 | 一句话 | 成长后会发生什么 |
|---|---|---|
| **顺序契约不牢** | 用 `srvAt`（毫秒时间戳）当同步游标 | 同毫秒撞号、跨页漏数据——已经踩过两次，只能靠"末组完整性保护"打补丁；记录量上去后补丁越补越难 |
| **写放大 + 无幂等** | push 逐条 upsert、50 条一包、串行；重试 = 重放 | 一个班 45 人结清就是 45 次写；批量导入或网络抖动重试时，历史版本会被"合法的重复写"污染 |
| **无索引规范 + 无观测** | `where(orgId + srvAt>since)` 无复合索引；云函数里 0 行日志、0 个 traceId | 集合到十万级后 pull 走全表扫→延迟涨→撞 20 轮上限→**同步悄悄变不全**；而服务端没有任何告警能告诉你这件事 |

**目标架构一句话**：保持"客户端为真相源"不变，把服务端从**"按时间戳扫增量"**升级为**"按机构有序变更日志（seq）汇合 + 幂等去重 + 可对账"**，并把单一 453 行的 `syncv2` 拆成「网关 + 领域函数 + 后台任务」，配套索引规范、可观测性与容灾演练。

**演进分三期**，每期独立上线、独立回滚，P0 不改协议（1 周内可完成，收益最大）。

## 1. 现状盘点（基于代码事实，不是设想）

### 1.1 组件与规模

| 云函数 | 行数 | 职责 | 触发方式 |
|---|---|---|---|
| `syncv2` | 453 | **核心**：身份绑定、邀请码、push/pull 同步、版本历史与回滚、服务端硬约束 | 小程序 `callFunction` |
| `backup` | 390 | 每日全量备份（云存储分片）、过期清理、分步恢复 | 定时器 03:00 + 小程序/后台 |
| `admin` | — | 电脑端后台：HTTP 服务，GET 出单页、POST 走 JSON；账号口令 + 会话表 | HTTP / 小程序 |
| `aiEval` | 216 | AI 评语生成 | 小程序 |
| `secCheck` | 52 | 文本/图片内容安全 | 小程序 |
| `family` | 91 | 家长订阅消息通知 | 小程序 |
| `stuImport` | 131 | 学生批量导入 | 小程序 |
| `sync` | 87 | 旧版同步（保留兼容） | 小程序 |

### 1.2 数据面

- 业务集合 9 个：`orgs / members / terms / classes / courses / students / enrollments / records / templates`
- 支撑集合：`users`（openid → orgId 绑定）、`invites`、`history`（4 类核心对象的版本历史，保留 10 版）、`admin_sessions`（后台会话，7 天）、`backups`（每日备份清单）、`admin_accounts`
- 多租户：`orgId` 单一分区键，出厂号 `org1`，新机构首次上云由 `hello` 发放随机号
- 删除：全量软删（`removed / removedAt / removedBy`）+ 回收站还原 + 批次回滚
- 同步：push 逐条 upsert（批内 `srvAt` 严格递增，跨实例靠末组保护）；pull 拉 `srvAt > since`，每集合 100 条、最多 20 轮；冲突用整条 LWW（`updatedAt` 新者胜）
- 备份：每日 03:00 分集合打包（2000 条/片）到云存储，清单一天一条，保留 30 天；恢复只写回不删除

### 1.3 已经做得好的部分（不要动）

1. **local-first**：客户端先落盘再同步，弱网可用——这是培训机构场景的正确选择，任何时候都不要退回"必须联网才能录入"。
2. **软删 + 回收站 + 版本历史**：误删可逆，核心资产有后悔药。
3. **服务端硬约束**（`checkCore`：ORG_ROOT / MEM_TAKEN / OWNER_EXISTS / DUP_NO）：客户端绕不过去。
4. **备份分集合分片 + 独立 tag 命名空间**：避开了 60 秒超时与"恢复到今天自杀"两个坑。
5. **拒绝不静默**（`rejected[] → meta.sync.rejects`）：同步拒绝会被人看到。

## 2. 风险矩阵

按「发生概率 × 影响 × 修复成本」排序。R1–R3 属结构性，必须在客户变多之前处理。

| # | 风险 | 证据 | 触发条件 | 影响 | 等级 |
|---|---|---|---|---|---|
| **R1** | 同步游标依赖时间戳 | `syncv2/index.js:342`（批内递增）、`:419`（末组保护） | 并发写同一集合 | 同步漏数据且难复现；每次并发增长都要加固一层 | 🔴 P0 |
| **R2** | 无索引规范 | 仓库无任何索引文档；pull 查询为 `where({orgId, srvAt: gt})` | 单集合 > 1 万条 | 全表扫 → pull 变慢 → 撞 20 轮上限 → **数据不全但界面正常** | 🔴 P0 |
| **R3** | 写放大 | `utils/sync.js:134`（50 条/包、串行、逐条 upsert） | 批量导入、结清一课、弱网重试 | 一次导入 500 条 = 500 次 DB 写；耗时线性增长，易撞 60 秒 | 🟠 P1 |
| **R4** | 无幂等键 | push 无 opId，重试即重放 | 网络超时但服务端已成功 | 版本历史被重复写污染；`history` 里出现"假冲突" | 🟠 P1 |
| **R5** | 服务端零观测 | `syncv2` 内 `console.log` 0 处、无 traceId、无错误上报 | 任何线上异常 | 只能靠用户反馈发现问题；备份"没备上"无人知晓 | 🔴 P0 |
| **R6** | 单体云函数 | 453 行承载 8 类职责 | 任何改动 | 改一行要重部署全部；无法独立扩容；审查成本高 | 🟠 P1 |
| **R7** | 环境未隔离 | 测试与生产共用 `cloud1` 环境 | 做演练/试新协议 | 测试数据污染生产；无法灰度 | 🟡 P2 |
| **R8** | 媒体访问控制 | 云存储 fileID 直接落库、分享即读 | 链接外泄 | 学生照片可被非成员访问 | 🟡 P2 |
| **R9** | 后台会话在业务库 | `admin_sessions` 与业务同库 | 后台被爆破 | 无独立审计、无 IP 白名单 | 🟡 P2 |
| **R10** | 配额硬顶 | 单环境并发/QPS、数据库单集合建议上限 | 客户数 × 上课高峰 | 某天早高峰集体超时 | 🟡 P2（有拐点，见 §7） |

## 3. 目标架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ L0 客户端（微信小程序）                                        │
│  本地库(storage 分片) · 脏集合写队列 · 同步引擎 · 冲突横幅      │
│  原则：永远可离线录入；同步只做「把本地状态推上去 + 拉别人的」   │
└───────────────────────────┬──────────────────────────────────┘
                            │ 唯一入口：api.gateway（鉴权/限流/幂等/traceId）
┌───────────────────────────▼──────────────────────────────────┐
│ L1 接入层  api / gateway                                      │
│  · 统一鉴权：openid → 机构与角色（一次解析，全域复用）          │
│  · 统一限流：按 openid / orgId 双维度令牌桶                    │
│  · 统一幂等：opId 去重（写）/ 请求指纹缓存（读）               │
│  · 统一出口：{ok, code, msg, data, traceId} 单一响应契约       │
└───────┬───────────────────┬───────────────────┬───────────────┘
        │                   │                   │
┌───────▼──────┐  ┌─────────▼────────┐  ┌───────▼──────────────┐
│ L2 领域服务   │  │                  │  │ L3 支撑服务           │
│ identity     │  │ academic         │  │ content              │
│ 成员/邀请/绑定│  │ 班级/课程/学生   │  │ 记录/模板/媒体        │
│              │  │ 报名/学期        │  │ 历史/回滚             │
└───────┬──────┘  └─────────┬────────┘  └───────┬──────────────┘
        └───────────────────┼───────────────────┘
                            │ 共享 lib（schema 单一来源 / 权限 / 校验）
┌───────────────────────────▼──────────────────────────────────┐
│ L4 数据层                                                     │
│  主库：9 业务集合（orgId 分区，seq 有序）                      │
│  日志：changes（变更日志）· ops（幂等去重）· history（版本）   │
│  派生：counters（按机构取号）· 统计读模型（可选，P3）          │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ L5 异步与保障层                                                │
│  jobs：backup（每日）· reconcile（对账）· notify（outbox 泵）  │
│  monitor：错误率 / P95 / 同步健康 / 备份状态 → 告警            │
└──────────────────────────────────────────────────────────────┘
```

**关键取舍**：接入层仍是"一个云函数"，不是微服务。**理由**：微信云开发的冷启动、配额、调用计费都按函数算——拆成十几个小函数会让冷启动与成本翻倍，而收益（独立扩容）在这个量级用不上。**拆分目标是"职责边界"，不是"进程边界"**：先按 `lib/` 模块拆清（同一函数内），再在 L2 里把身份与内容拆成两个函数（这两块的增长曲线完全不同）。

### 3.2 服务职责边界

| 服务 | 拥有的数据 | 对外动作 | 不该做的事 |
|---|---|---|---|
| `gateway` | 无（只读鉴权上下文） | 路由、限流、幂等、traceId | 不写业务表 |
| `identity` | `members` `invites` `users` | hello/whoami/invite*/成员 CRUD | 不碰记录 |
| `academic` | `classes` `courses` `students` `enrollments` `terms` | 学生/班级/课程/报名读写、导入 | 不生成评语 |
| `content` | `records` `templates` `history` | 记录写入/发布/修改、模板、回滚、历史 | 不改学生归属 |
| `jobs` | `backups` `changes` `ops` | 备份、对账、清理、通知泵 | 不接受外部业务写入 |
| `admin` | `admin_sessions` `admin_accounts` | 后台页面与接口 | 直连业务集合必须走 orgId 校验 |

## 4. 同步协议 v2（现在的）→ v3（目标）

同步是这套系统的**唯一关键路径**，其余都是外围。协议必须满足四个性质：**无洞（no gap）、可续（resumable）、幂等（idempotent）、可对账（reconcilable）**。现在只做到了"近似无洞 + 可续"。

### 4.1 协议对比

| 性质 | v2 现状 | v3 目标 |
|---|---|---|
| 游标 | `srvAt`（毫秒时间戳） | `seq`（每机构单调递增整数） |
| 顺序保证 | 批内递增 + 末组保护（补丁） | 取号在事务内完成，**天然全序** |
| 续传 | `more` 标记 + 最多 20 轮 | `{changes, nextSeq, hasMore}`，无轮次上限（有字节预算） |
| 幂等 | 无 | 每条写带 `opId`，`ops` 表去重（TTL 7 天） |
| 冲突 | 整条 LWW | 字段级 LWW + 冲突留痕（供后台解释"为什么我改的被覆盖了"） |
| 拒绝 | 回传客户端，仅客户端可见 | 回传 + 服务端 `audit` 留痕 + 指标计数（可告警） |
| 对账 | 无 | 每日 `reconcile`：服务端每集合 `(orgId) 计数 + maxSeq` vs 客户端上报，偏差即告警 |

### 4.2 v3 写入路径（语义描述，非代码）

1. 客户端把脏文档按依赖序分组（orgs → members/terms → classes/courses → students/enrollments → records/templates）。
2. 每组 ≤ 200 条 / ≤ 1 MB，带批次 `opId`（批次号 + 机构号 + 客户端 id）。
3. 服务端在一个事务里：① `ops` 查重（命中直接返回上次结果，**重放安全**）→ ② `counters` 取号（`seq = last + 1 ... last + n`）→ ③ 逐条 upsert，写入 `seq`、`updatedAt` → ④ 核心集合写 `changes` 与 `history` → ⑤ `ops` 记结果。
4. 返回 `{accepted, rejected[], seq}`。拒绝项带**稳定错误码**（`ORG_ROOT` / `DUP_NO` / `MEM_TAKEN` / `OWNER_EXISTS` / `VALIDATION`），客户端按码提示，不再匹配中文字符串。
5. 单次执行有 **30 秒软预算**：到点就停在安全边界（整条文档粒度），返回 `nextBatch` 标记，客户端接着推下一批——**永不因超时半条写入**。

### 4.3 v3 读取路径

1. `pull(sinceSeq, limit)` → 读 `changes where orgId = X and seq > sinceSeq order by seq`，每轮不超过 500 条或 1 MB。
2. 返回 `{changes:[{c, id, seq, d}], nextSeq, hasMore}`；`nextSeq` 取"最后一条完整返回的 seq"，**只有推进到该值才落盘游标**。
3. `changes` 是**追加日志**，可安全重读（客户端按 `seq` 幂等应用），所以"网络断在中间"不会再产生"游标跳过头"的风险。
4. 保留 30 天的 `changes`；超过 30 天没同步的客户端走**全量快照**（`backup` 已有的分片机制复用），而不是回放日志——这就是"离线太久的设备"的正确出路。

### 4.4 迁移策略（关键：不停机、可回滚）

- **双写过渡期**：v2 的 `srvAt` 与 v3 的 `seq` 同时写（`seq` 只增不删），客户端按 `meta.sync.proto` 决定用哪套。
- **按机构灰度**：`orgs.syncProto = 'v3' | 'v2'`，先给自己的测试机构开，再给一家真实客户，再全量。
- **回滚**：把 `syncProto` 改回 `v2` 即可，v2 路径完全保留至少 8 周。
- **停止条件**（任一即回滚）：pull 的 P95 > 1.5 秒、拒绝率 > 0.5%、`reconcile` 出现偏差。

## 5. 多租户与数据隔离

### 5.1 分区键

`orgId` 是**唯一**分区键，所有查询必须带上——这一条现在守得很好，继续用门禁保证（建议在审查规则里把"云函数内 `db.collection(` 后必须出现 `orgId` 条件"升级为 lint 规则）。

### 5.2 索引规范（当前完全缺失，**最高性价比的 P0**）

| 集合 | 索引 | 服务哪种查询 |
|---|---|---|
| 全部 9 个业务集合 | `(orgId ASC, seq ASC)` | v3 pull 增量 |
| 全部 9 个业务集合 | `(orgId ASC, srvAt ASC)` | v2 过渡期 pull |
| `students` | `(orgId, no)` **唯一** | 学号查重（`DUP_NO` 硬约束靠它兜底） |
| `students` | `(orgId, removed, clsIds)`（如云开发不支持数组索引则退化 `(orgId, removed)`） | 班级学生列表 |
| `records` | `(orgId, sid, session)`、`(orgId, cid, date)` | 学生历史、班级课次 |
| `members` | `(orgId, openid)`、`(orgId, role)` | 换机恢复、负责人唯一性校验 |
| `changes` | `(orgId, seq)` | pull（唯一热点） |
| `ops` | `(orgId, opId)` 唯一 + TTL | 幂等去重 |
| `history` | `(orgId, c, id, at DESC)` | 版本历史页 |
| `backups` | `(orgId, date)` | 备份列表 |

**验收**：在控制台对每个集合执行一次 `pull` 等价查询，返回时间 < 50ms（1 万条数据量）且命中索引（云开发控制台可看慢查询）。

### 5.3 大客户隔离阈值

| 阶段 | 条件 | 做法 |
|---|---|---|
| A | < 50 机构、单机构 < 2000 学生 | 共享环境 + `orgId` 隔离（现在） |
| B | 单机构 > 2000 学生 或 > 20 万记录 | **独立云环境**（org → env 映射表），备份与配额互不影响 |
| C | 单机构 > 50 万记录 或 需要跨机构复杂报表 | 该机构的数据迁到独立库（TDSQL/MySQL），同步协议不变（`changes` 抽象让它可换存储） |

## 6. 可靠性工程

### 6.1 失败语义（必须写死，不能靠猜）

| 场景 | 语义 | 客户端行为 | 服务端行为 |
|---|---|---|---|
| 网络超时（未知是否写成功） | **可重试**（幂等保护） | 指数退避 + 抖动，重试 5 次 | `opId` 命中即返回上次结果 |
| 服务端 5xx | 可重试 | 同上 | 记 `audit` + 指标 |
| 硬约束拒绝（DUP_NO 等） | **不可重试** | 展示原因，让用户改 | `audit` 留痕 |
| 内容安全拦截 | 不可重试 | 提示改文案 | 记拦截原因（不含原文） |
| 读超时（pull） | 可重试 | 游标不推进，从原 seq 重试 | — |
| 配额/限流（429） | 延迟重试 | 退避 ≥ 30 秒 | 返回 `Retry-After` |

**原则**：只有"读"允许服务端内部重试；"写"的重试权归客户端，靠幂等保证安全。

### 6.2 超时预算

| 动作 | 目标 P95 | 硬上限 | 到上限时 |
|---|---|---|---|
| `pull`（单轮） | ≤ 400ms | 8s | 返回已拿到的 `nextSeq`（`hasMore: true`） |
| `push`（200 条） | ≤ 1.2s | 30s 软预算 | 停在文档边界，返回 `nextBatch` |
| 记录保存（含 AI 预检） | ≤ 800ms | 8s | AI 走异步，主流程不等 |
| 备份（单集合） | ≤ 20s | 45s 预算 | 存 `partial`，下轮接力 |
| 恢复（单集合） | ≤ 25s | 50s | 返回 `nextFrom` |

### 6.3 容灾目标与演练

| 指标 | 现状 | 目标 | 达成手段 |
|---|---|---|---|
| **RPO**（最多丢多久） | ≤ 24 小时（每日备份） | **≤ 15 分钟** | `changes` 日志可回放（v3 落地后自动具备） |
| **RTO**（多久恢复） | 未知（从未演练） | **≤ 2 小时** | 分步恢复 + 恢复脚本 + 演练记录 |
| 单集合损坏 | 可恢复到昨天 | 可恢复到"任一分钟" | v3 日志 + 每日快照 |

**季度演练**（必须有记录，写进 `docs/drills/YYYY-QN.md`）：
1. 在**独立环境**用最近一次备份全量恢复，核对 `students/records` 条数与抽取 10 条字段一致性；
2. 模拟"误删一个班 30 人"→ 回收站还原 → 核对报名与记录是否一并回来；
3. 模拟"服务端拒绝 100 条"→ 客户端是否能完整展示；
4. 记录实测 RTO，超过 2 小时就找瓶颈。

> 备份的最大谎言是"备份成功了"。**只有真恢复过一次的备份才算备份。**

### 6.4 灰度与开关

每个高风险动作都要有服务端开关（存 `orgs.flags`）：`syncProto`、`pushBatch`（50 → 200）、`reconcile`、`notify`。开关的好处是**出问题不用发版**——小程序发版有审核延迟，这是本项目的硬约束。

## 7. 可观测性（当前是 0，必须补）

### 7.1 三条链路必须能追踪

1. **同步**：客户端生成 `traceId`（一次同步会话一个），贯穿 push/pull 每次调用；日志一行 JSON：`{traceId, openid, orgId, action, batch, ms, accepted, rejected, err}`。
2. **备份**：每次运行记 `{date, orgId, status, counts, failed[], ms}`，并写 `backups` 清单（已有），失败必须**告警**出去。
3. **后台**：登录、批量改、导出、恢复——全部记 `admin_audit`（谁、何时、改了什么、IP）。

### 7.2 指标与告警阈值

| 指标 | 采集点 | 告警阈值 | 通道 |
|---|---|---|---|
| 云函数错误率 | 每函数出口 | 5 分钟 > 2% | 企业微信机器人 |
| `push` 拒绝率 | 同步服务 | 1 小时 > 1% | 同上 |
| `pull` P95 延迟 | 同步服务 | > 1.5s 持续 10 分钟 | 同上 |
| 同步"停摆" | 客户端上报心跳 | 某机构 > 24 小时无任何 sync | 同上 |
| 备份状态 | `backups` 清单 | 当日 04:00 仍无 `ok` 记录 | 同上（**这是最重要的一条**） |
| 数据库容量 | 每日统计 | 使用率 > 70% | 同上 |
| 单集合增长 | 每日统计 | 日增 > 5 万条 | 通知（评估分库） |

**实现成本极低**：一个 `utils/metrics.js` 打点 + 一个 `jobs/monitor` 每 10 分钟聚合 + 一个 webhook。**但它是所有其他改进的前提**——没有观测，你无法判断 v3 是成功还是失败。

## 8. 容量与成本模型

假设目标形态：**20 家机构 × 平均 300 学生 × 每人每学期 20 条记录**。

| 项 | 估算 | 说明 |
|---|---|---|
| `students` | 6,000 条 | 单集合完全无压力 |
| `records`（1 年） | 240,000 条 | 单集合 ~10 万级是云开发舒适区上沿 |
| 年写入次数（DB） | ~30 万次 upsert + 30 万次 pull 读 | 折合每天约 1,600 次写 / 1,600 次读 |
| 云存储 | 照片 ~20 万张 × 300 KB ≈ 60 GB | **成本主项**，需要压缩与清理策略 |
| 每日备份增量 | 全量 ~1.5 GB/机构/年（分片） | 保留 30 天 → 峰值 ~120 GB |

**结论**：数据库在 20 家机构内不是瓶颈，**存储与流量才是**。因此：

- 照片上传前压到长边 ≤ 1280、质量 80（已在做则确认落地）；
- 云存储按机构分目录 + 90 天冷归档（原图 → 缩略图策略）；
- 备份保留 30 天后自动清理（已有），但要**按机构算**，避免一家大客户把配额吃光。

**拐点信号**（出现任一就该考虑换存储引擎）：单集合 > 30 万条、日写 > 5 万次、`pull` P95 > 1 秒、或需要跨机构聚合报表。

## 9. 安全基线

| 项 | 现状 | 目标 |
|---|---|---|
| 服务端鉴权 | 每次调用解析 openid → 成员；`admin` 用账号口令 + 会话 | 保持不变，把解析结果收敛到 gateway 一处 |
| 越权防护 | 所有查询带 `orgId`；`checkCore` 硬约束 | 增加 lint 规则：云函数内出现无 `orgId` 的写查询即失败 |
| 后台会话 | 存业务库 `admin_sessions`，7 天 | 独立集合 + 记 IP/UA；敏感操作二次口令；错 5 次锁（已有）保留 |
| 媒体访问 | fileID 直接落库 | 私有读 + 临时链接（`getTempFileURL`），家长端链接 10 分钟过期 |
| PII | 家长手机号明文 | 导出/后台展示脱敏（中间 4 位打码），完整值仅负责人可查 |
| 审计 | 无 | `admin_audit` + `ops`（写操作）保留 180 天 |
| 密钥 | 云开发内置，无外泄 | 严禁把 AppSecret/私钥写进仓库（`deploy.js`、CI 已排除） |

## 10. 演进路线

### P0 · 稳定性底座（不改协议，1 周，收益最大）

| # | 事项 | 验收 |
|---|---|---|
| 1 | 建全部索引（§5.2 表） | 控制台慢查询为空；pull 单轮 < 50ms（1 万条数据） |
| 2 | 补服务端结构化日志 + traceId | 一次同步能在日志里串起来（客户端 traceId 传入） |
| 3 | 备份/同步关键指标告警 | 故意让备份失败一次，5 分钟内收到告警 |
| 4 | 恢复演练一次并记录 RTO | `docs/drills/2026-Q4.md` 有实测数字 |
| 5 | `ops` 幂等表 + push 带 opId | 同一批重复推送两次，DB 写入次数不变、历史不重复 |
| 6 | push 批量 50 → 200、并发 2 路 | 500 条导入耗时下降 ≥ 60% |

> 这 6 条**不改数据模型、不改协议**，全部可灰度、可回滚。做完之后，系统从"靠人盯"变成"有仪表盘"。

### P1 · 同步 v3（2–3 周）

| # | 事项 | 验收 |
|---|---|---|
| 1 | `counters` 取号 + `changes` 日志 + `seq` 游标（双写） | v3 机构 pull 与 v2 结果一致（影子比对 24 小时零差异） |
| 2 | 客户端 `proto` 开关 + 全量快照兜底 | 断网 3 天后同步能自愈（走快照） |
| 3 | `reconcile` 每日对账 | 连续 7 天零偏差 |
| 4 | 灰度顺序：测试机构 → 1 家真实 → 全量 | 任一阶段出现回滚条件立即回 v2 |

### P2 · 职责拆分与异步化（2 周）

| # | 事项 | 验收 |
|---|---|---|
| 1 | `syncv2` 拆 `identity` / `content` / `gateway` | 单函数 < 300 行；改动面下降，审查可分工 |
| 2 | outbox 模式做通知（家长订阅消息） | 发布记录不再等通知结果；失败自动重试 3 次 |
| 3 | 后台审计 + PII 脱敏 + 媒体临时链接 | 安全审计清单全绿 |
| 4 | 独立测试环境 | 演练与灰度在测试环境预演 |

### P3 · 规模化（按需）

读模型物化（机构统计不再实时算）、大客户独立环境、冷数据归档、成本优化。

## 11. 决策记录（ADR 摘要）

**ADR-1：不迁出云开发，继续 serverless。**
理由：当前量级下自建 Node + MySQL 的成本主要在**运维与安全**，而团队只有一个人；云开发的"零运维 + 内置鉴权 + 按量"在这个阶段收益远大于其限制。迁出条件写死在 §8 拐点信号里。

**ADR-2：坚持 local-first，不改为"在线优先"。**
理由：培训场景发生在教室，网络不可靠是常态；"打不开就不能录"会直接失去客户。所有服务端设计都必须假设"客户端可能离线数天"。

**ADR-3：用变更日志（seq）取代时间戳游标。**
理由：时间不是顺序契约。`srvAt` 已经两次导致漏数据（同毫秒撞号、跨页不全），每次修补都靠"末组保护"这种启发式。`seq` 让"无洞、可续、可对账"变成结构性保证，而不是补丁。代价是每条写要多一次取号（可批量）、每个集合多一个复合索引。

**ADR-4：不上消息队列 / Kafka。**
理由：云开发没有原生队列；用 `changes` + 定时泵（outbox）已满足"异步通知、统计、清理"的需求，引入外部中间件等于给自己加一个必须运维的单点。规模到 P3 再评估。

**ADR-5：写入重试权归客户端，服务端只做幂等。**
理由：服务端重试写入会掩盖客户端状态机的问题，并放大"半写"风险；幂等键让客户端可以放心重试，责任边界清晰。

**ADR-6：备份必须"可恢复"才算完成，写进验收。**
理由：本项目已经出现过"备份写成功但恢复链路断"的 P0（见 `docs/reviews/2026-11-05-backup-review.md`）。因此备份功能的验收标准是**恢复演练通过**，不是"跑完不报错"。
