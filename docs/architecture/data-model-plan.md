# 橙果课堂 · 数据模型与底层数据系统规划（v1.0）

> 编写：2026-11-05 · **纯规划，不含代码改动**
> 目标：**阶段一（课后服务、老师录课录成果）现在就要把数据打对；阶段二（题库系统）只加表、不改表、不迁数据。**
> 依据：`utils/db/schema.js`（VERSION = 8，10 类实体）、`utils/db/*`（local-first 数据层）、`cloudfunctions/syncv2`（同步协议）、`docs/architecture/backend-architecture.md`（后端架构方案）。

---

## 0. 结论先行

### 三条主线

| 主线 | 一句话 | 现在不做会怎样 |
|---|---|---|
| **① 分出"学科 / 知识点"两个一级维度** | 题库是按知识点组织的，而知识点必须**跨机构共享且 ID 稳定** | 题库无法共享、无法统计掌握度；以后再补要重挂全部历史数据 |
| **② "评价"与"作答"分开建模** | `records` 是老师写的观察性评价（文本+照片+主观分）；题库产生的是结构化作答（题目+对错+得分）。两者**不要合并成一张万能表** | 合并后 `records` 会变成 25 个字段的表，一半永远为空；同步、导出、统计全被拖慢 |
| **③ 派生数据可重建** | 掌握度、错题本、统计都由"作答 + 评价"算出来，**不同步、可随时 drop 重算** | 一旦当成"真相"存起来，口径一改就永远修不回来 |

### 一句话架构

> **三层分离：内容层（学科/知识点/题目）→ 活动层（课程/班级/作业/练习）→ 结果层（课堂记录/作答/掌握度）。**
> 结果层只追加、不改写；内容层版本化、不原地改；派生层随时可丢。

### 阶段一（现在）只需要做 5 件小事（约 1 天，不改任何现有行为）

1. `courses` 加 `subjectId`（默认按课程名猜一个，猜不中留空）
2. 新建 `subjects` 集合（机构内学科，7 条默认数据）
3. 新建 `knowledge_points` 集合（先只在阶段一末期录入少量，不建界面也行）
4. `records` 加 `scoreScale`（满分口径，默认 100）与 `kpIds: []`（先留空）
5. `schema.js` 升级为**实体注册表 + 数据字典自动生成**（防"文档写了两天就过期"——这事已经发生过一次）

> 这 5 件事的共性是：**现在做只是加空字段/空表，成本接近零；阶段二再补，等于把全量历史数据重挂一遍**。

## 1. 产品两阶段对数据的要求

### 阶段一：课后服务（当前主线）

老师上课 → 录成果（照片/语音/评语/五档等级）→ 发布家长端 → 结清本次课 → 生成周期成绩单。

数据的四个特征：
- **人少、条多**：一个机构几十到几百学生，但每人每节课一条记录 → `records` 是增长最快的表。
- **主观性**：分数是老师打的 0-100，不是对错题算出来的 → 只能做趋势，不能做"知识点掌握度"。
- **证据导向**：照片、语音是核心资产（家长买单的就是"看得见"）。
- **弱网离线**：教室网络差，local-first 是硬约束。

### 阶段二：题库系统（下一步）

能力清单与它们依赖的数据：

| 能力 | 依赖的数据 | 数据特征 |
|---|---|---|
| 题库管理（题目/选项/解析/图片） | `questions` + `question_versions` + 知识点标签 | 内容为主，**一次写、多次读** |
| 组卷/布置作业 | `papers` / `assignments`（按知识点或难度选题） | 引用而非复制 |
| 学生作答 | `submissions`（一次提交一个文档，内嵌逐题答案） | **写多读少，但行数可控** |
| 自动判分 | 答案 + 判分规则（客观题自动、主观题人工） | 规则要可追溯 |
| 掌握度分析 | 按 `studentId × knowledgePointId` 汇总 | **派生数据，可重算** |
| 错题本 | 由作答中 `correct = false` 派生 | 派生 |
| 家校报告 | 记录 + 作答 + 掌握度合并 | 读模型 |

**关键结论**：题库不是"再加一个功能页"，它是**第二条数据主线**。如果不提前把"学科/知识点/题目/作答"的位置留出来，阶段二会撞三件事：知识点没地方挂、题目没有稳定 ID、作答和评价混在一张表里。

## 2. 现有模型盘点：六处会成为瓶颈

| # | 现状（代码证据） | 阶段二会怎样 | 现在改的成本 |
|---|---|---|---|
| **B1** | `course = { id, clsId, name }`，只有名字（`schema.js:normalizeCourse`）；没有学科 | 题库选题要"数学·五年级·分数加减"，但没有学科维度 → 只能靠字符串匹配课程名 | **极低**（加一列 + 7 条默认学科） |
| **B2** | 没有任何"知识点"概念 | 题目无处归类、掌握度无法计算、错题本无法聚合 | **低**（加集合，先不填数据） |
| **B3** | `record.score` 只有一个数字，没写满分口径（`normalizeRecord`） | 将来混入"满分 10 分的小测"，平均分会算错；无法区分"85/100"与"8.5/10" | **极低**（加 `scoreScale`，默认 100） |
| **B4** | `id` 是**每机构从 1 自增的数字**（`normalizeClass/Student/Record` 都是 `num(r.id, 0)`） | 公共题库跨机构共享时 ID 必然冲突；迁移、合并机构时会撞号 | **低**（现在加 `gid` 字段，老数据可批量生成；以后再加要改全部外键） |
| **B5** | 媒体直接存 fileID 数组在记录里（`photos[] / videos[] / audio`） | 题目图片、作答照片会让媒体散落在十几张表里，无法做配额、清理、CDN | **中**（先立 `media` 台账，阶段一只登记不改造） |
| **B6** | 没有数据保留期与归档策略；软删的 `removed` 行永不清理 | 作答数据一年能到百万级，软删记录越堆越多，备份体积与恢复时间线性上涨 | **低**（定策略，不用改代码） |

> 还有一处**不是瓶颈但要记住**：`records` 已经有 `type` 字段（`RECORD_TYPES = ['achievement']`），这是当初留下的扩展点——阶段二加"作业/测验"时**不需要改表**，只需往数组里加值。这个决定省了一次全量迁移，说明"留字段不留逻辑"的用法是对的，题库设计沿用同样思路。

## 3. 六域数据模型

```
┌── 组织域 ────────────────────────────────────────────────┐
│ orgs ── members（人×机构×角色） ── users（账号）           │
│   └ flags / syncProto / 容量配额                          │
└──────────────────────────────────────────────────────────┘
┌── 内容域（阶段二核心，现在只建骨架）─────────────────────┐
│ subjects（学科） ── knowledge_points（知识点树，可共享）   │
│        └ questions（题） ── question_versions（不可变版本）│
│ templates（评价模板，已有）                                │
└──────────────────────────────────────────────────────────┘
┌── 教学域（已有，微调）───────────────────────────────────┐
│ terms（学期） ── classes（班级） ── courses（课程 → subject）│
│ students（学生） ── enrollments（课时账本）                │
└──────────────────────────────────────────────────────────┘
┌── 活动域 ─────────────────────────────────────────────────┐
│ records（课堂记录，已有）   assignments（作业/练习，新）    │
│ papers（试卷/题组，新）                                    │
└──────────────────────────────────────────────────────────┘
┌── 结果域（只追加）────────────────────────────────────────┐
│ submissions（一次提交 = 一个文档，内嵌逐题答案）            │
│ mastery（掌握度，派生）   wrong_book（错题本，派生）        │
└──────────────────────────────────────────────────────────┘
┌── 平台域 ─────────────────────────────────────────────────┐
│ public_banks / bank_grants（公共题库授权）                 │
│ media（媒体台账）  audit（审计）  backups（备份，已有）      │
└──────────────────────────────────────────────────────────┘
```

**为什么这样切**：内容域是"平台资产"（可共享、变化慢、谁都能读）；教学域是"机构资产"（强隔离）；结果域是"只追加的事实"（谁都不能改）。三类数据的**生命周期、隔离级别、同步方式完全不同**——混在一起就是现在这类系统最常见的塌方点。

## 4. 表设计

约定（所有新表强制）：
- 公共审计字段：`orgId / createdAt / updatedAt / removed / removedAt / removedBy`（已有 `audit()`）
- 同步三件套：`updatedAt` + `srvAt` + `removed`（缺一个就同步不到）
- 命名：集合名小写复数；外键一律 `xxxId`；金额/课时用整数分或整数课时，**不用浮点**
- 类型：时间戳用毫秒整数；日期用本地 `YYYY-MM-DD` 字符串（沿用现有 `date`，避免 UTC 偏一天）
- 每张表必须在注册表里登记：`同步 / 派生 / 保留期 / 索引 / 谁能写`

### 4.1 现有表：需要增补的字段

| 表 | 增补字段 | 类型 | 说明 | 影响 |
|---|---|---|---|---|
| `orgs` | `subjectIds: []` | array | 本机构启用的学科 | 无（空数组 = 全启用） |
| | `flags: {}` | object | 功能开关（`syncProto / quizBeta / notify`） | 已在上轮架构方案定义 |
| | `quota: {}` | object | 配额（学生数/存储/月题量） | 用于限流与告警 |
| `courses` | `subjectId` | int | 所属学科 | 新增，默认 0=未指定 |
| | `level` | string | 年级/阶段（如"五年级"） | 题库按年级筛题用 |
| `students` | `grade` | string | 在读年级 | 题库难度匹配；不影响现有逻辑 |
| | `school` | string | 就读学校（课后服务要向学校提交时用） | 可选 |
| `records` | `scoreScale` | int | 满分口径，默认 100 | 统计分母 |
| | `kpIds: []` | array | 关联知识点（阶段二填） | 打通"课堂评价 ↔ 知识点" |
| | `workId` | int | 若这条记录对应一次作业/测验 | 0 = 纯课堂观察 |
| `members` | `subjectIds: []` | array | 该老师教的学科 | 权限细化备用 |
| `templates` | `subjectId` | int | 模板适用学科 | 0 = 通用 |

> **批量迁移策略**：全部字段都可为空/默认值，老数据升级时自动填默认；`subjectId` 先按课程名做一次"关键词映射"（书法/美术/数学…），命中就填，不命中留 0，**不阻塞任何人**。

### 4.2 新增 · 内容域

#### `subjects`（学科）

| 字段 | 类型 | 必填 | 索引 | 说明 |
|---|---|---|---|---|
| `id` | int | ✓ | 主键 | 机构内自增 |
| `gid` | string | ✓ | 唯一（与 orgId 复合） | 全局 ID，如 `sub_math`（内置学科用固定值，跨机构一致） |
| `name` | string | ✓ | — | 数学 / 语文 / 书法 / 美术 … |
| `kind` | string | | — | `academic`（学科类）/ `art`（艺术类）/ `skill`（技能类）——决定题库题型集合 |
| `sort` | int | | — | 排序 |
| 审计字段 | | | | |

内置 7 条（随首次使用种子化）：语文、数学、英语、物理/化学（或"科学"）、书法、美术、编程。

#### `knowledge_points`（知识点树）

| 字段 | 类型 | 必填 | 索引 | 说明 |
|---|---|---|---|---|
| `id` | int | ✓ | 主键 | 机构内自增（机构私有知识点） |
| `gid` | string | ✓ | 唯一（orgId + gid） | 全局稳定 ID，**题目永久引用它，永不复用** |
| `orgId` | string | ✓ | 复合 | `platform` = 公共知识点 |
| `subjectId` | int | ✓ | 复合 | 所属学科 |
| `parentId` | int | | 复合 | 父节点（0 = 根） |
| `path` | string | ✓ | 复合 | 物化路径 `数学/小学/数与代数/分数`（**查询子树的唯一手段**） |
| `depth` | int | ✓ | — | 层级深度，0 起 |
| `name` | string | ✓ | — | 知识点名 |
| `grade` | string | | 复合 | 适用年级（"三年级"~"六年级"，空 = 全年级） |
| `code` | string | | — | 外部映射码（对齐课标/教材章节，做数据交换用） |
| `sort` | int | | — | 同层排序 |
| `source` | string | | — | `platform` / `org` |

**为什么要 `gid` 而不是只用自增 `id`**：公共知识点由平台维护，各机构按 `gid` 引用；一旦用自增 `id`，平台发新节点、某机构又自建了同号节点，数据就会串。这是**不可逆决策**（一改就要重挂所有题目与作答）。

**为什么要有 `path`**：云开发没有递归查询。要"这个知识点及其全部子节点的掌握度"，只能靠 `path` 前缀匹配（`path like '数学/小学/数与代数/%'`）。没有它，每层都要发一次请求。

#### `questions`（题目本体）与 `question_versions`（不可变版本）

`questions`（当前态，供列表/搜索/选题）

| 字段 | 类型 | 必填 | 索引 | 说明 |
|---|---|---|---|---|
| `id` | int | ✓ | 主键 | |
| `gid` | string | ✓ | 唯一 | `q_` + 全局唯一串 |
| `orgId` | string | ✓ | 复合 | 私有题=机构号；公共题=`platform` |
| `subjectId` | int | ✓ | 复合 | |
| `kpIds: []` | array | ✓ | 复合（数组索引） | 可挂多个知识点 |
| `type` | string | ✓ | 复合 | `single` 单选 / `multi` 多选 / `blank` 填空 / `judge` 判断 / `calc` 计算 / `essay` 解答 / `draw` 绘画（艺术类） |
| `difficulty` | int | ✓ | 复合 | 1–5 星 |
| `grade` | string | | 复合 | 适用年级 |
| `stem` | string | ✓ | — | 题干（纯文本，公式用行内标记） |
| `stemMedia: []` | array | | — | 题干图片 fileID（走 `media` 台账） |
| `options: []` | array | | — | `{key:'A', text, media}`，客观题用 |
| `answer` | object | | — | `{keys:['A'], text:'', value:''}` 标准答案 |
| `analysis` | string | | — | 解析 |

| `source` | string | | — | 出处（自编/教材/真题/导入） |
| `currentVersion` | int | ✓ | — | 当前版本号 |
| `usageCount` | int | | — | 被引用次数（选题时避开重复） |
| `status` | string | | 复合 | `draft / published / archived` |
| 审计字段 | | | | |

`question_versions`（**只追加、永不改**）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int | |
| `qid` | int | 题目 id |
| `gid` | string | 题目 gid |
| `version` | int | 版本号 |
| `snapshot` | object | 完整题目快照（含题干/选项/答案/解析/分值） |
| `changedBy` / `changedAt` / `reason` | | 谁改的、为什么 |

**为什么要版本化**：题目一旦被学生答过，改题干或答案会让历史统计失真（"这题正确率 30%"到底指哪一版？）。规则：**已发布且被引用过的题目，编辑 = 生成新版本，旧版本冻结**；`submissions.detail[].qVersion` 记录作答时看到的版本。这是题库类系统最容易被忽略、也最贵的一处返工。

#### `records`（已有，不动结构）

阶段二只填两个新字段：`workId`（对应哪次作业/测验）、`kpIds`（这条观察评到了哪些知识点）。**不把作答塞进 records。**

### 4.4 新增 · 结果域（只追加）

#### `submissions`（一次提交 = 一个文档，逐题答案内嵌）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `gid` / `orgId` | | |
| `assignmentId` | int | 哪次布置 |
| `studentId` | int | 谁 |
| `attemptNo` | int | 第几次提交（允许重做） |
| `startedAt` / `submittedAt` | int | |
| `detail: []` | array | 逐题：`{qid, qGid, qVersion, answer:{}, correct:bool, score:num, maxScore, kpIds:[], ms}` |
| `rawScore` / `totalScore` | num | 得分/满分 |
| `autoScore` / `manualScore` | num | 自动判分与人工判分分开记（可追溯） |
| `graded` | bool | 是否判完（主观题可能延后） |
| `source` | string | `student` 学生自答 / `teacher` 老师代录 / `paper` 纸质扫描 |
| 审计字段 | | |

**关键设计：整卷内嵌，不按题一行**
- 行数从「学生 × 题数」降到「学生 × 提交次数」——小一个数量级。
- 一次提交天然原子（不会出现"这卷答了 3 题、那 2 题丢了"）。
- 代价：跨题聚合要在应用层展开（可接受，因为聚合结果会落到 `mastery`），且单文档不超过 16MB（一张卷 ≤ 200 题，安全）。

#### `mastery`（掌握度 · 派生，不同步）

| 字段 | 类型 | 说明 |
|---|---|---|
| `orgId` / `studentId` / `kpId` | | 复合主键语义 |
| `attempts` / `correct` / `wrong` | int | 分母与分子 |
| `accuracy` | num | 正确率（0–1） |
| `weighted` | num | 按难度加权后的掌握度（难题权重高） |
| `level` | string | `未掌握 / 待巩固 / 基本掌握 / 熟练`（**阈值集中在一处定义**） |
| `lastAt` | int | 最近一次作答时间 |
| `decay` | num | 时间衰减因子（可选，阶段二后期） |

写入规则：**只有服务端能写**；由 `submissions` 增量更新 + 每日全量重算兜底（两条路径结果必须一致，偏差即 bug）。

#### `wrong_book`（错题本 · 派生）

`{orgId, studentId, qid, qGid, kpIds[], firstWrongAt, lastWrongAt, wrongCount, correctedAt, status}` —— 状态机：`待订正 → 已订正 → 巩固中 → 已掌握`。

### 4.5 新增 · 平台域

| 表 | 作用 | 关键字段 |
|---|---|---|
| `public_banks` | 公共题库（平台发布，供机构引用） | `id, name, subjectId, grade, itemCount, version, publishedAt` |
| `bank_grants` | 机构 → 公共题库授权 | `orgId, bankId, grantedAt, expiresAt, scope` |
| `media` | 媒体台账（照片/语音/题目图/作答图 统一登记） | `id, gid, ownerType, ownerId, fileID, bytes, mime, width, height, sha256, orgId, uploadedAt, archivedAt` |
| `audit` | 服务端审计（写操作、拒绝、后台操作） | `at, traceId, orgId, actorId, action, target, result, why` |

`media` 现在就可以建（只登记，不改造现有上传路径）：它是**存储配额、去重、冷归档、孤儿清理**的唯一抓手。没有台账，照片永远不知道自己属于谁，也就永远删不干净。

### 4.6 全局 ID 策略（不可逆决策，务必现在定）

| 对象 | 主键 | 全局 ID | 规则 |
|---|---|---|---|
| 机构 | `orgs.id`（字符串） | 同左 | `org_` + 10 位（已有） |
| 学生/班级/记录等机构内对象 | `id` 自增 int | 不设 | 机构内唯一即可，同步时由 `orgId + id` 定位 |
| 学科 | `id` | `gid` | 内置固定（`sub_math`）；自建用 `sub_<org>_<n>` |
| 知识点 | `id` | `gid` | `kp_` + base32(时间戳+序号)，**永不复用** |
| 题目 | `id` | `gid` | `q_` + base32；公共题与私有题同一命名空间 |
| 试卷 | `id` | `gid` | `p_` + base32 |
| 提交 | `id` | `gid` | `s_` + base32 |

> 为什么机构内对象不设全局 ID：它们永远不跨机构，加了反而让同步与迁移复杂。**"共享的东西才需要全局 ID"**——这条边界要写进规范，否则将来会有人给学生也加 gid，然后到处吵架。

## 5. 索引与典型查询

| 场景 | 查询 | 必需索引 |
|---|---|---|
| 今日待录 | `records where orgId, cid, session` | `(orgId, cid, session)` |
| 学生档案历史 | `records where orgId, sid order by date desc` | `(orgId, sid, date desc)` |

| 知识点子树 | `knowledge_points where path like 'A/B/%'` | `(orgId, path)` |
| 按知识点选题 | `questions where orgId, kpIds contains, status` | `(orgId, status, difficulty)` + 数组索引 |

## 6. 底层数据系统的六条规则

这部分比表结构更重要：**表可以加，规则一旦破了就救不回来。**

### 规则 1 · schema 单一来源 + 数据字典自动生成

现状：`utils/db/schema.js` 是唯一真相，但**文档是手写的**，已经过期过一次（审查标准 v1.0 说"240 项断言/8 个套件/CI 没门禁"，实际 513/24/早就有）。

目标：
- `schema.js` 内每实体声明 `{ fields, indexes, sync, derived, retention, writer }`；
- `npm run docs:schema` 从注册表生成 `docs/data-dictionary.md`（表/字段/类型/索引/谁可写）；
- 门禁：**注册表与字典不一致 → CI 失败**。文档过期就此变成不可能。

### 规则 2 · 迁移必须兼容 N-2 个客户端版本

小程序发版有审核延迟，旧客户端会与新库共存数周。因此：
- 只做**加字段、加表、加默认值**；不做删字段、改语义、改类型；
- 语义变化用"双写 + 开关"过渡（如 `srvAt` → `seq`、`course` → `subjectId`）；
- `VERSION` 递增时，`migrate.js` 必须幂等（现有迁移脚本已是这个风格，继续保持），且每条迁移都要有一条断言：**用 V7 的数据跑 V8 的迁移，连续跑两次结构一致**。

### 规则 3 · 引用完整性由代码守卫，不靠自觉

- 每个外键都必须有"孤儿检测"：`records.sid → students.id`、`courses.clsId → classes.id`、`questions.kpIds → knowledge_points.gid`、`submissions.assignmentId → assignments.id`。
- 现有 `utils/db/audit.js`（只读体检）是正确雏形 → 扩展成**每新增一张表就加一条孤儿检查断言**。
- 理由：云开发没有外键约束，删了学生留下 300 条孤儿记录，只有体检能发现。

### 规则 4 · 派生数据可重建（drop & rebuild）

- `mastery` / `wrong_book` / 统计读模型：**不同步、不备份、可整表删除重算**。
- 每个派生表必须有 `rebuild()` 入口和一条断言：`重建后的结果 = 增量维护的结果`（差一条都算 bug）。
- 这条规则的意义：**口径一定会改**（什么叫"掌握"？正确率 80% 还是加权 0.7？）。可重建 = 改口径只改一个函数；不可重建 = 改口径要写数据修复脚本，还可能修错。

### 规则 5 · 保留期与归档

| 数据 | 保留 | 到期动作 |
|---|---|---|
| 业务主数据（机构/成员/学生/班级/报名） | 永久（软删保留 90 天后物理清理） | 归档到冷存储 |
| `records` + 媒体 | 3 年 | 媒体转冷归档，记录保留 |
| `submissions` | 3 年（可配置） | 汇总到 `mastery` 后归档明细 |
| `changes`（同步日志） | 30 天 | 过期清理；超期客户端走全量快照 |
| `ops`（幂等） | 7 天 | TTL 清理 |
| `audit` | 180 天 | 归档 |
| `backups` | 30 天 | 自动清理（已有） |

**现在就要写**：软删行没有物理清理策略，等于数据库只增不减。备份体积、恢复时间、同步日志都会跟着涨。

### 规则 6 · 谁能写，写在哪

| 数据 | 谁可写 | 写在哪 |
|---|---|---|
| 机构主数据、成员权限 | 负责人/管理员 | 客户端写入本地 → 同步到云 |
| 学生/班级/课程/报名 | 负责人/管理员/老师（按范围） | 同上 |
| `records` | 有该班录入权限的老师 | 同上（`checkCore` 服务端兜底） |
| 题目/知识点/试卷（机构） | 教研角色（新）或负责人 | 后台/小程序 → 云 |
| 题目（公共） | 平台运营 | 仅后台 |
| `submissions` | 学生本人（或老师代录） | 客户端 → 云（**只追加，不允许改历史提交**，改＝新 `attemptNo`） |
| `mastery` / `wrong_book` / 统计 | **只有服务端** | 云函数，客户端只读 |
| `audit` | 只有服务端 | 云函数 |

## 9. 容量与成本（题库阶段）

假设：**20 家机构 × 300 学生 × 每周 20 题 × 40 周**。

| 项 | 估算 | 结论 |
|---|---|---|
| 公共题库题目 | 3–5 万 | 单集合无压力 |
| 机构私有题目 | 每机构 2 千 → 合计 4 万 | 同上 |
| 提交（submissions） | 20 × 300 × 40 = **24 万/年** | 单文档内嵌答案 → 可行；2 年后考虑按学年分集合（`submissions_2027`） |
| 若按题一行（answers） | 24 万 × 20 = **480 万/年** | ❌ 不可接受 —— 这就是选"整卷内嵌"的量化理由 |
| 掌握度（mastery） | 20 × 300 × 200 知识点 ≈ 120 万 | 偏高 → 只给"有作答记录"的学生建行（稀疏化），实际约 10–20 万 |
| 存储（题目图 + 作答图） | 每年 30–50 GB | 成本主项，必须压图 + 冷归档 |

**分表规则**：`submissions` 单集合 > 50 万条时按学年分集合；`mastery` 按 `orgId` 哈希分 4 片（超过 50 万行时）。

## 10. 不可逆决策清单（现在定，以后不改）

| # | 决策 | 一旦错了的代价 |
|---|---|---|
| 1 | **知识点/题目用 `gid` 全局 ID，永不复用** | 全部题目与历史作答要重新挂接 |
| 2 | **题目版本化，已答过的题只能新增版本** | 历史统计口径永久污染 |
| 3 | **作答整卷内嵌，不按题一行** | 行数膨胀 20 倍，跨表聚合性能塌方 |
| 4 | **掌握度是派生数据，可重算** | 口径一改就修不回来 |
| 5 | **知识点用物化路径 `path`** | 云开发无递归查询，子树统计做不出来 |
| 6 | **`records` 与作答分离** | 万能表，一半字段永远为空 |
| 7 | **时间：日期用本地 `YYYY-MM-DD`，时刻用毫秒整数** | 跨时区偏一天，统计口径错 |
| 8 | **软删语义：`removed` + `removedAt` 批次** | 回收站还原"复活"错条目 |

## 12. 三件事的拍板结果（2026-11-05）

1. **阶段一现在做那 5 件事 → 做，已完成。**
   成本约一天，收益是阶段二"只加表、不改表、不迁数据"。第 5 条（数据字典门禁）已经顺带解决了文档过期问题：字段与注册表不一致时 CI 直接红。

2. **题库先"只做机构私有"，预留公共结构 → 定了。**
   阶段二建 `public_banks` / `bank_grants` 两张表但**不做公共题库运营**：新机构开箱有题的价值很高，但版权与教研运营是另一门生意，等有 3 家以上机构再用公共题库摊薄成本。
   现在只保证 gid 与 `source`（platform / org）留好：将来公共题库上线，题目能直接按 gid 跨机构引用，不需要重挂历史数据。

3. **课后成果暂不向学校正式提交 → 定了（阶段一不做）。**
   阶段一的口径是"家长可见、机构可用"，不做学校维度的正式报送。理由：一旦要报送，就要提前定格式、学校维度、隐私授权与撤回机制，这会把一个两周能上线的东西拖成三个月。
   影响可控：`students.profile` 是自由字段，学校/年级随时能放进去；正式的 `students.school` + 周期报告导出放到阶段二第 ⑥ 步（家校报告）一起做，那时才有真实使用数据决定格式。**表结构不用改，只加字段。**

> 三条结论的共同点：能推后的一律推后，但"推后会变贵"的一律现在做（gid、path、scoreScale、作答与评价分离）。
