# 橙果小程序 · 代码审查标准与流程 v1.0

> 制定日期：2026-11-03
> 适用：`chengguo-miniprogram` 全部代码（`pages/` `utils/` `components/` `cloudfunctions/` `server/` `tests/` `deploy.js`）
> 配套：`project-engineering-file.md`（问题登记表与 ADR）、`docs/code-review-report-2026-11-03.md`（首次全量审查）

---

## 0. 一句话定位

审查不是"挑错"，是在合并前拦住三类问题：**用户数据丢了**、**权限被绕过**、**审核发不出去**。
除此之外的问题都是建议，可以排期，但不能挡住发版。

这个项目最难的部分已经做对了（数据层分层、权限单闸门、fail-closed、架构守卫）。剩下的风险几乎全部集中在**存储容量天花板**和**上云前的安全边界**上——审查标准就是围着这两处加密。

---

## 1. 三条红线（不可协商）

任何一条被破坏 = P0，**不论影响面多小、不论多急**。急的时候唯一的合法操作是"把功能关掉再发"，不是"先上再修"。

| # | 红线 | 具体含义 | 破坏示例 |
|---|---|---|---|
| R1 | **数据不可静默丢失** | 用户点了保存，就必须真的存下来。存不下必须当场报错，不能只在 console 留一行 | `wx.setStorageSync` 抛错被 catch 吞掉，返回 false 无人检查，界面照旧提示"已保存" |
| R2 | **权限不可绕过写** | 每个写操作都要有统一闸门；每个"目标对象"都要校验它属于当前身份。只校验"谁能做这类事"不校验"对谁做"= 没校验 | 编辑记录时改了 `sid`，但只校验了原记录的归属，没校验新 `sid` 是否可见 |
| R3 | **演示数据不可污染真实数据** | 两套数据物理分离，任何路径都不能写串 | 合并云端数据时没判 `isSandbox()`，演示态把远端真实数据写进内存 |

> R3 已经在 2026-11-03 通过独立命名空间 + `ctx.deny()` 首条拦截实现，审查时要防的是**新代码倒退回去**（例如将来新增一个 `import`/`导出`/`批量改` 走 `core.coll` 而不判模式）。

## 2. 缺陷分级

| 级别 | 定义 | 处理时限 | 谁能豁免 |
|---|---|---|---|
| **P0 阻断** | 触发 R1/R2/R3；或必然导致审核被拒、线上白屏、数据错乱 | 修复前不得发版 | 无人可豁免 |
| **P1 应修** | 特定条件下会出真问题（数据泄露给不该看的人、操作非原子、重复提交、越权路径当前 UI 不可达但闸门缺校验） | 两个版本内 | 负责人书面记录理由 + 排期 |
| **P2 建议** | 可维护性、性能、体验瑕疵，不影响正确性 | 排期即修 | 负责人可延后 |
| **P3 nit** | 命名、注释、风格；有 lint 就该由工具管，不该出现在评论里 | 顺手 | 直接忽略 |

**判定口诀**：问三个问题——
1. 用户会不会丢东西？（会 → 至少 P1，静默则 P0）
2. 数据会不会跑到不该看到的人眼前？（会 → P0/P1）
3. 这次发版会不会被审核打回？（会 → P0）

## 3. 自动门禁（硬性，人工审查之前先过）

这三条不通过，代码不进 main。**门禁的价值在于让第 4 节的人工清单只用来找"机器找不到的东西"**。

### G1 · 回归全绿

```bash
npm test          # 等价 node tests/run.js，8 个套件
npm run lint      # 自建自检（约定漂移、死代码、页面绕开数据层）
npm run check     # lint + test，提交前一条命令
```

当前基线：**236 项断言**（数据层 27 / 权限 45 / 学期 30 / P0 27 / 页面级 53 / 演示隔离 18 / 加固 27 / 架构守卫 9），另有 `npm run lint`（82 文件）。
要求：
- 全绿才能提交，**不允许"先提交再修"**；
- 新增断言数只增不减。删断言必须在提交信息里写明删了哪条、为什么；
- 修 bug 的顺序是**先写一条会红的断言 → 修到绿**。不是先修再补测试（那样测试永远只能证明"现在没崩"，证明不了"原来确实坏了"）。

### G2 · 架构守卫不红

`tests/verify_arch.js` 是这套架构的法律条文，红了通常意味着有人为了省事破了分层：

| 守卫 | 防的是什么 |
|---|---|
| require 无环 | 小程序里循环 require 会拿到半成品模块，表现为随机 `undefined` |
| 依赖严格下行（LAYER 表） | 领域模块互相调用 → 逻辑重新长回一团 |
| 页面不直接读写 storage | 绕过数据层 → 权限过滤、演示隔离、软删除全部失效 |
| 数据层只有 `storage.js` 碰 `wx` | 这是"换云端只改一个文件"的唯一保证 |
| 对外 API 面完整 + 门面 ≤260 行 | 防止 `index.js` 重新膨胀成千行大文件 |

**新增领域模块时必须先在 LAYER 表登记层级**。如果发现"只能向上引用"，那是边界划错了——改边界，不要加环。

### G3 · 改动必须有对应断言

按改动类型对照：

| 改了什么 | 至少补什么 |
|---|---|
| `utils/db/*` 的写函数 | 一条"没权限/被拦下"的负向断言 + 一条"正常写入"的正向断言 |
| 权限规则 `permissions.js` | 一条 fail-closed 断言（没被显式授权时必须拒绝） |
| 页面交互逻辑 | 一条页面级断言（`tests/verify_pages.js` 里真实加载 Page 对象） |
| 存储/容量相关 | 一条"写入失败时怎么办"的断言（目前是空白，见报告 P0-1） |
| 演示数据相关 | 一条磁盘级断言（真实 key 里零演示行） |

## 4. 人工审查清单

只查机器查不到的东西。每一项都要能回答"是/否"，答"否"就写下位置。

### A · 写入路径（对应 R1/R2）

- [ ] 新的写函数是否走了 `ctx.deny(action, target)`？有没有直接 `perms.can(...)` 绕过闸门？（历史上真出过：`recordSave` / `recordMarkSent`）
- [ ] `target` 是否带上了**真正会被改的那个对象**？编辑类操作要校验"新目标"，不只是"老对象"。
- [ ] `core.persist()` 的返回值有没有人看？失败时用户看到的是什么？
- [ ] 一个用户动作做了多处写（如结转向导），中途失败会留下什么半成品？有没有补偿或至少一个"可重试"的入口？
- [ ] 软删除是否贯穿：删班级/学生时，课程、报名、成员绑定、记录引用是否同步处理？

### B · 权限与数据范围（对应 R2）

- [ ] **读**也过滤了吗？（`utils/db/index.js` 的承诺是"读也过滤，不只拦写"；`enrollments` 目前是例外）
- [ ] 返回给页面的对象，是否只包含该身份该看的内容？（家长能看到的字段 = 自己孩子的 + 已发布的）
- [ ] 有没有页面在用 `_all()` / `db.coll()` / `db.raw()` 这类"内部接口"？它们不进权限层，用了就是绕过。
- [ ] 跨机构隔离：读走 `oc()`（按 orgId 过滤），写走 `core.coll()`（保留他机构数据）。用反了会串数据。
- [ ] 身份切换（`users.switchTo`）当前等价于"谁拿到手机谁是负责人"。本地阶段可接受，**上云前必须移到服务端**——这条写进检查单，每次上云相关改动都要重看。

### C · 存储与容量（对应 R1，本项目的最大坑）

- [ ] 新增的数据是否落进已经接近上限的集合？（微信硬限制：**单 key 1MB，总量 10MB**）
- [ ] 这个字段会不会无界增长？（`note` 无长度上限、`profile` 无长度上限、`photos` 上限 9 但路径可以很长）
- [ ] 媒体文件：`USER_DATA_PATH` 上限约 200MB，当前**没有清理入口**，删除照片只解引用不删文件。新增媒体功能必须回答"满了怎么办"。
- [ ] 落盘失败时，界面是否还显示成功？（R1 的核心）

### D · 页面层

- [ ] WXML 里有没有方法调用（`arr.indexOf(id)`、`s.name.slice()`）？渲染层会直接抛异常，且开发者工具不报错。
- [ ] `setData` 传的是不是整个大对象？（一次几百 KB 会明显卡顿，列表页尤其）
- [ ] 同一个按钮连点两次会发生什么？保存类操作有没有 `saving` 锁？
- [ ] `wx.createInnerAudioContext()` 有没有 `destroy()`？页面 `onUnload` 有没有清定时器/音频/录音？
- [ ] 页面 `onShow` 的数据初始化是否也能在"直接 onShow 不走 onLoad"时成立？（测试就是这么调的）

### E · 合规（发版前必看，不属于代码质量但会拦发版）

- [ ] 新增的隐私接口（相册/相机/录音/位置/手机号）是否已在公众平台《用户隐私保护指引》里声明？
- [ ] 未成年人信息：本项目采集的是**儿童姓名、照片、家长手机号/微信**。上架前需要监护人同意的说明，且不能默认勾选。
- [ ] UGC 内容安全：记录的文字与照片会发给家长（对外传播），审核阶段通常要求接入 `msgSecCheck` / `imgSecCheck`。目前**完全没有**。
- [ ] 新增页面是否需要在小程序后台配置业务域名 / 是否触发类目要求（教育类目需资质）？

### F · 测试质量

- [ ] 断言测的是"行为"还是"实现"？测实现（比如断言内部数组顺序）会在重构时误报。
- [ ] 有没有覆盖**失败路径**？（存储满、权限拒绝、文件不存在、云端返回 null）
- [ ] 测试之间有没有共享可变状态？（`require.cache` 清理会让页面和测试持有两个 db 实例，历史上踩过）

### G · 可读性

- [ ] 注释写的是**为什么**，不是**做了什么**。（这个项目的注释水平是资产，别退化成 `// 设置数据`）
- [ ] 领域模块 > 400 行、页面 > 400 行，是否该拆？（现有阈值：门面 260 / 模块 500）
- [ ] 新增的魔法值（颜色、时长、上限）是否统一到常量或 token？页面里现有 19 处硬编码色值，新增的不该再加。

### H · 交付

- [ ] 改动是否需要重新上传体验版？真机验证项写清楚（哪几页、点哪里、看什么）。
- [ ] 有没有影响老数据？需要迁移的话，`schema.VERSION` 加一，`migrate.build` 里写升级路径，并且**不能重播演示数据**。
- [ ] 回滚路径是什么？（本地数据类改动没有"回滚"，只有"前向修复"——所以更要在发版前想清楚）

## 5. 变更规模分级（决定审查深度）

| 级别 | 判断标准 | 审查方式 | 耗时 |
|---|---|---|---|
| **S 小改** | 样式、文案、单个页面交互；不碰 `utils/db/` | 自审 + G1/G2 | 3 分钟 |
| **M 中改** | 单个领域模块或单个页面的逻辑；新增字段 | 自审 + 清单 A/B/F + G1/G2 | 15 分钟 |
| **L 大改** | 权限规则、数据模型、迁移、存储层、云端、发布流水线 | 全清单 + 一次全量复审 + 真机验证清单 | 1 小时 |

`utils/db/permissions.js`、`utils/db/storage.js`、`utils/db/core.js`、`utils/db/schema.js`、`deploy.yml` —— 这五个文件只要动，**一律按 L 处理**。它们是这个项目的地基，改动成本被严重低估过。

## 6. 流程

### 6.1 单人开发（当前形态，轻量版）

```
改代码
 └─ 3 分钟自审：过一遍第 4 节里与本次改动相关的分组
 └─ npm test                     ← G1，必须全绿
 └─ 提交（约定式信息，见 6.3）
 └─ 发版前 10 分钟：过 E 组（合规）+ H 组（交付）
 └─ 上传体验版 → 真机逐项点一遍（清单写在提交信息里）
 └─ 上线后 24h：看有没有人反馈"存了但没了"
```

**明确不做的**：不搞 PR 流程、不搞双人复核、不搞评审会。单人项目上重流程只有一个结果——两周后开始绕过它。
但有两条必须守：**G1 全绿才提交**、**P0 不许带着发版**。

### 6.2 多人协作时升级

一旦有第二个人碰代码，立刻切到：

1. `main` 设保护：禁止直推，必须 PR；
2. PR 必须过 G1/G2（CI 里跑 `npm test`，见 6.4）；
3. 至少 1 人复核，**改 `utils/db/` 的 PR 必须复核者本地跑一遍 `npm test`**；
4. 复核人有否决权，但没有"帮你改"的义务——提意见、给方案，改动由作者做（作者才会记得）。

### 6.3 提交信息规范

沿用现有的中文描述式标题（这个仓库的历史提交质量不错，保持即可）。要求三点：

1. 第一行说清**做了什么**（不写"优化""调整"这种没有信息量的词）；
2. 正文说清**为什么**：原来的问题是什么、会造成什么后果；
3. 末尾写**验证方式**：跑了哪个套件、多少项断言、真机点了哪几页。

带 P0/P1 编号的修复，标题里带上编号，方便回溯：

```
修复记录集合触顶后静默丢数据（P0-1）

问题：records 整表存一个 key，超过 1MB 后 setStorageSync 抛错被吞掉，
界面仍提示"已保存"，重启后记录消失。
做法：落盘失败向上返回，由 records.save 转成"存储空间已满"的明确提示；
同时把写入结果纳入返回值，页面不再假设成功。
验证：新增 3 项断言（模拟抛错的 storage），全量 212 项通过。
```

### 6.4 发布流水线的门禁（当前缺失，见报告 P0-3）

现状：`.github/workflows/deploy.yml` 在 push 到 main 时**直接上传小程序新版本，不跑测试**。
这意味着 G1/G2 全靠人记性——只要有一个人忘了，未验证的代码就是体验版。

建议顺序（三步走，不必一次到位）：

1. **第一步（今天就能做）**：在 upload 步骤前插入 `npm test`，失败即中断；
2. 第二步：给流水线加 `concurrency` 互斥，避免连推两次时旧版本后上传覆盖新版本；
3. 第三步：主包体积门禁（`< 1.9MB` 时告警，因为上限 2MB，当前 1.7MB）。

> 这一条是流程问题不是代码问题，所以**必须写进标准**：自动发版的前置条件里没有测试，等于没有门禁。

### 6.5 审查节奏

| 时机 | 做什么 |
|---|---|
| 每次改动 | 第 4 节对应分组 + G1/G2 |
| 每个版本发布前 | E 组（合规）+ H 组（交付）+ 真机清单 |
| 每两周 | 一次"无目的复审"：只读代码不修，专找累积的问题（本次报告就是这种） |
| 每次出线上问题 | 先定级（P0/P1）→ 修 → **补一条断言** → 登记到 `project-engineering-file.md` |

## 7. 审查意见的写法

统一格式，避免"这里不太对"这种无法执行的评论：

```
🔴 P0 · 数据静默丢失
位置：utils/db/storage.js:44 / utils/db/records.js:92
现象：setStorageSync 抛错被 catch 后返回 false，但 core.persist 的返回值
      在 records.save 里没有人检查，界面照旧提示"已保存"。
为什么：单 key 上限 1MB（微信硬限制），按当前体量约 1 个月触顶。触顶后每条新
      记录都只存在于内存，重启即消失——用户不知道自己丢了东西。
建议：1) persist 失败向上抛/返回；2) records.save 把失败转成明确文案；
      3) 容量到 80% 时在「我的」页给出提示与导出入口。
验证：mock storage 抛错，断言 save 返回 ok:false 且提示含"存储空间"。
```

要求：
- **位置精确到文件:行**；
- **为什么** 要能让人明白"不修会怎样"，不是复述代码；
- **建议** 给方向，不强加实现；
- **验证** 说清怎么证明修好了（能变成断言最好）；
- 一件问题一条，不要把五件事塞进一段话。

审查结束给一句总评 + 一句下一步，别只丢一堆问题。

## 8. 缺陷登记与度量

所有 P0/P1 进 `project-engineering-file.md` 的编号表（现有 `CR-001`…`CR-009` 格式），列：编号 / 位置 / 现象 / 影响 / 状态。
状态只允许三种：`未修（Px）` / `已修（版本）` / `挂起（原因）`。

每次发版记录四个数字，用来判断质量是变好还是变差：

| 指标 | 当前 | 含义 |
|---|---|---|
| 断言数 | 236 | 只增不减 |
| 未修 P0 数 | 1（P0-3 CI 门禁，项目方决定暂缓至提审前） | 必须为 0 才能发版 |
| 未修 P1 数 | 1（P1-9 内容安全，待云环境） | 趋势向下即可 |
| 主包体积 | 0.85MB | 上限 2MB，超 1.9MB 就要处理 |

## 9. 什么时候可以破例

只有一种情况：**线上已经坏了，先止血**。

止血时的规则：
1. 只做**最小改动**，不顺手重构；
2. 必须在 24 小时内补断言 + 补文档；
3. 如果止血方案本身触碰红线（比如"先把权限判断注释掉"），**改为关掉功能**——关功能是可接受的，放权限不是。
