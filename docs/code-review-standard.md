# 橙果 · 代码审查标准与流程 v2.0

> v1.0：2026-11-03 · v2.0：2026-11-05
> 适用：`chengguo-miniprogram` 全部代码（`pages/` `utils/` `components/` `cloudfunctions/` `tests/` `tools/` `deploy.js`）
> 配套：`docs/handoff.md`（接续与已踩过的坑）、`project-engineering-file.md`（缺陷登记）、`.github/pull_request_template.md`（PR 证据）、`tools/review.js`（审查包）

**为什么升到 v2.0**：v1.0 写完两天，代码从本地单机长成了「手机端 + 云函数 + 多机构 + 每日备份」，v1.0 里的事实全部过期（240 → 513 项断言、8 → 24 个套件、CI 门禁从"缺失"变成"已落地"），而且它没有覆盖新增的最大风险面：**两端数据一致性**和**备份能不能真的恢复**。v1.0 的三条红线、缺陷分级、意见写法仍然有效，保留。

---

## 0. 一句话定位

审查不是挑错，是在合并前拦住四类事故：**用户数据丢了**、**权限被绕过**、**演示数据污染真实库**、**云端/备份在关键时刻不可靠**。

其余问题都是建议，可以排期，但不能挡住发版。**审查的产出不是"意见数量"，是"发版后没人丢东西"。**

---

## 1. 四条红线（不可协商）

任何一条被破坏 = P0，不论影响面多小、不论多急。急的时候唯一合法操作是**把功能关掉再发**，不是"先上再修"。

| # | 红线 | 具体含义 | 本项目真实破坏方式 |
|---|---|---|---|
| R1 | **数据不可静默丢失** | 点了保存就必须真存下来；存不下必须当场报错 | `readColl` 把"读异常"当成"没有数据"，下一次写入把残缺数据覆盖回磁盘（已修） |
| R2 | **权限不可绕过** | 每个写操作过统一闸门；除"能不能做"还要校验"对谁做" | 家长重装后 `me` 默认撞上负责人 `userId`，被当成负责人（已修：改 openid 优先） |
| R3 | **演示数据不可污染真实库** | 两套数据物理分离，任何路径都不能写串 | 合并云端数据时不判演示态，把远端真实数据写进内存 |
| R4 | **云端与备份必须"拉得回、恢复得出"** | 写了 `updatedAt` 就必须写 `srvAt`；备份必须有一条被验证过的恢复路径 | push 整批共用一个 `srvAt`，跨 100 条分页边界后永远拉不到（已修）；备份能生成但从未恢复过一次 = 等于没有备份 |

R4 的两个子项：
- **两端一致**：任何服务端/后台写入都要盖 `updatedAt` + 严格递增的 `srvAt`，否则手机端增量游标捞不到，表现是"电脑上改了，手机看不见"。
- **可恢复性**：新增备份/快照/回收站，必须同时给出恢复路径，并在测试里真的恢复一次。

## 2. 缺陷分级

| 级别 | 定义 | 处理时限 | 谁能豁免 |
|---|---|---|---|
| **P0 阻断** | 触发 R1–R4；必然导致审核被拒、白屏、数据错乱 | 修复前不得发版 | 无人 |
| **P1 应修** | 特定条件下出真问题（范围泄露、非原子、重复提交、越权路径当前 UI 不可达但闸门缺校验） | 两个版本内 | 负责人书面记理由 + 排期 |
| **P2 建议** | 可维护性、性能、体验瑕疵 | 排期即修 | 负责人可延后 |
| **P3 nit** | 命名、注释、风格 | 顺手 | 忽略（有 lint 就不该出现在评论里） |

**判定四问**：
1. 用户会不会丢东西？（会 → 至少 P1；静默 → P0）
2. 数据会不会跑到不该看的人眼前？（会 → P0/P1）
3. 换一台手机 / 恢复一次备份之后，数据还在吗？（不在 → P0）
4. 这次发版会不会被审核打回？（会 → P0）

## 3. 自动门禁（硬性，人工审查之前先过）

门禁的意义是**让第 5 节的人工清单只用来找机器找不到的东西**。

### G1 · 全绿才能提交

```bash
npm run check     # lint + size + test，一条命令
npm test          # 24 个套件 / 513 项断言
npm run lint      # 122 个文件的自建自检（约定漂移、死代码、页面绕开数据层）
npm run size      # 主包 1068.8 KB / 2 MB（52.2%）
```

- 全绿才能提交，**不允许"先提交再修"**；
- 断言数只增不减。删断言必须在提交信息里写清删了哪条、为什么；
- 修 bug 的顺序：**先写一条会红的断言 → 修到绿**。先修再补只能证明"现在没崩"，证明不了"原来确实坏了"。

### G2 · 架构守卫不红

`tests/verify_arch.js` 是架构的法律条文，红了通常意味着有人为了省事破了分层：

| 守卫 | 防的是什么 |
|---|---|
| require 无环 + 依赖严格下行（LAYER 表） | 领域模块互相调用 → 逻辑长回一团；循环 require 拿到半成品模块 |
| 页面不直接读写 storage、数据层只有 `storage.js` 碰 `wx` | 绕过数据层 = 权限过滤 / 演示隔离 / 软删除全部失效 |
| 对外 API 面完整 + 门面 ≤ 260 行 + 模块 ≤ 500 行 | 防止门面重新膨胀成千行大文件 |
| 送达文案断言（拦「已发送」） | 订阅消息没接通前不许对家长撒谎 |

新增领域模块必须先在 LAYER 表登记层级。发现"只能向上引用"= 边界划错了，改边界，不要加环。

### G3 · 改动必须有对应断言

| 改了什么 | 至少补什么 |
|---|---|
| `utils/db/` 的写函数 | 一条越权/被拦的负向断言 + 一条正常写入的正向断言 |
| `utils/db/permissions.js` | 一条 fail-closed（没被显式授权必须拒绝） |
| `utils/db/storage.js` / 快照 | 一条"写入失败/读坏时怎么办"的断言 |
| `cloudfunctions/syncv2` | 一条越权机构断言 + 一条 LWW/游标断言 + 一条硬约束拒绝断言 |
| `cloudfunctions/backup` | 一条"过期只删备份、不动业务数据" + 一条恢复后时间戳盖新的断言 |
| `cloudfunctions/admin` | 一条"每条写入带 srvAt、每条 where 带 orgId"的源码纪律断言 |
| 页面交互 | 一条页面级断言（真实加载 Page 对象） |
| 演示数据相关 | 一条磁盘级断言（真实 key 里零演示行） |

### G4 · 审查包与 PR 证据

```bash
npm run review            # 生成审查包：按风险层分组 + 必查章节 + 门禁结果
npm run review -- --check # 顺带跑一遍 npm run check
```

PR 模板（`.github/pull_request_template.md`）必须填四项，缺一项视为未审查：

1. **改了什么 / 为什么**（原来的问题、不修会怎样）
2. **风险等级**（R0/R1/R2，由 `npm run review` 判定，作者确认）
3. **验证证据**（跑了哪个套件多少项；真机点哪几页、看什么）
4. **回滚或止血方案**（数据类改动没有回滚，只有前向修复——写清怎么修）

CI 的 `verify`（lint → test → size）已经是硬门禁，红了不允许上传体验版。

## 4. 变更风险分级（决定审查深度）

由路径自动判定（`tools/review.js`），**作者可以往上调，不可以往下调**。

| 级别 | 路径 | 审查方式 |
|---|---|---|
| **R0 地基** | `utils/db/permissions.js` `core.js` `storage.js` `schema.js` `ctx.js`；`cloudfunctions/syncv2/` `backup/` `admin/index.js`；`.github/workflows/` | 全清单 + 一次独立审查（AI 或第二人）+ 24h 冷却 + 真机验证 |
| **R1 领域** | 其余 `utils/db/*`、`utils/sync.js`、`utils/api.js`、`cloudfunctions/*/index.js`、`deploy.js` | 对应章节清单 + 一次独立审查 + G1/G2 |
| **R2 界面** | `pages/` `components/` `app.*` `assets/` | 自审 + G1/G2 + 页面级断言 |
| **R3 外围** | `docs/` `tests/` `tools/` `*.md` | 自审 + 门禁（改测试要检查断言只增不减） |

**R0 的判定不看行数**：`permissions.js` 改 3 行也可能放开通天的权限，改 300 行也可能只是加注释——按文件算，不按 diff 大小算。

## 5. 人工审查清单

只查机器查不到的。每条能回答"是/否"，答"否"就写下文件:行。

### A · 写入路径（R1/R2）

- [ ] 新的写函数是否走 `ctx.deny(action, target)`？有没有直接 `perms.can(...)` 绕过闸门？
- [ ] `target` 带的是**真正会被改的那个对象**吗？编辑类操作要校验"新目标"，不只是"老对象"。
- [ ] `core.persist()` / `writeColl` 的返回值有人看吗？失败时用户看到什么？
- [ ] 一个动作做了多处写（结清、批量录入、删班级），中途失败留下什么半成品？有补偿或可重试入口吗？
- [ ] 软删贯穿了吗：删学生/班级时，记录、报名、课程、家长绑定是否同批次处理？还原能否按批次补回？

### B · 权限与机构隔离（R2）

- [ ] **读也过滤**吗？（`db` 的承诺是"读也过滤"；`enrollments` 是历史例外）
- [ ] 返回给页面的对象只含该身份该看的内容吗？（家长 = 自己孩子 + 已发布）
- [ ] 有没有页面在用 `db.coll()` / `db.raw()` / `_all()` 这类内部接口？
- [ ] 跨机构：读走 `oc()`（按 orgId 过滤），写走 `core.coll()`（保留他机构数据）。用反了就是串数据。
- [ ] 云函数里 `orgId` 来自哪里？**客户端传的 orgId 一律不可信**，有 openid 时必须用 `users` 绑定的机构。
- [ ] "openid 为空 = 内部调用（定时器/服务端）"这条判断有没有被客户端伪造的可能？（客户端调用一定带 openid）

### C · 同步与云端一致（R4）

- [ ] 服务端 / 后台的每次写入都盖了新的 `updatedAt` **和** `srvAt` 吗？
- [ ] `srvAt` 是严格递增的吗？（同一毫秒多条 → 分页边界永久拉不到）
- [ ] 增量拉取的分页边界上，末组不完整时是否整组退回？
- [ ] LWW 合并有没有屏蔽写钩子（防回声）？软删行参与合并吗？
- [ ] 新增集合有没有同时加进 `COLLS`、`recycle`、备份清单、`ensureCollections` 四处？漏一处就会出现"同步了但没备份"或"备份了但恢复不了"。

### D · 备份与恢复（R4）

- [ ] 备份产物有清单吗？（能回答"哪天的、多少条、在哪个文件"）
- [ ] 保留期到了删的是**备份自己的东西**，还是顺手把业务数据也删了？
- [ ] 恢复只写回、不删除吗？（"回档"会静默吃掉备份之后的新数据）
- [ ] 恢复后 `updatedAt` / `srvAt` 变新了吗？否则手机端拉不到，还会拿旧值覆盖回去。
- [ ] 这条恢复路径**被测试真的跑过一次**吗？（不是"代码看起来对"）

### E · 页面层

- [ ] WXML 里有没有方法调用（`arr.indexOf(id)`、`s.name.slice()`）？渲染层直接抛异常且开发者工具不报错。
- [ ] `setData` 传的是不是整个大对象？
- [ ] 同一个按钮连点两次会怎样？保存类有没有 `saving` 锁？
- [ ] `wx.createInnerAudioContext()` 有没有 `destroy()`？`onUnload` 有没有清定时器/录音？
- [ ] `onShow` 单独调用（不走 `onLoad`）能不能成立？测试就是这么调的。
- [ ] 页签/入口新增后，`goTab` 之类的白名单里加了吗？（后台「数据安全」页签点了没反应，就是漏了这一条）

### F · 测试质量

- [ ] 断言测的是行为还是实现？（测实现会在重构时误报）
- [ ] 覆盖失败路径了吗？（存储满、权限拒绝、云端返回 null、网络断）
- [ ] 异步用例都 `await` 了吗？（不 await 会并发抢同一份内存库，红得莫名其妙）
- [ ] 测试之间有没有共享可变状态？（`require.cache` 会让页面和测试拿到两个 db 实例）

### G · 合规（发版前必看）

- [ ] 新增隐私接口（相册/相机/录音/位置/手机号）是否已在《用户隐私保护指引》声明？
- [ ] 未成年人信息（儿童姓名、照片、家长手机号/微信）是否有监护人同意说明，且不默认勾选？
- [ ] UGC 是否过内容安全（`secCheck`：文本 87014、图片）？
- [ ] 新页面是否触发类目/业务域名要求？

### H · 交付

- [ ] 需要重新上传体验版吗？真机验证清单（哪几页、点哪里、看什么）写进 PR 了吗？
- [ ] 影响老数据吗？要迁移则 `schema.VERSION` 加一、`migrate` 写升级路径、**不能重播演示数据**。
- [ ] 新云函数/改过的云函数，部署步骤写清了吗（上传依赖、触发器、环境变量、超时）？
- [ ] 回滚路径是什么？（数据类只有前向修复）

## 6. 流程

### 6.1 默认形态：一个人 + AI 审查（当前）

单人项目最怕两件事：**自己审自己**（等于没审）、**流程太重最后被绕过**。折中做法是把 PR 当成"审查单元"，不指望第二个人类：

```
拉分支 feat/xxx（不直接推 main）
 └─ 写代码（先补断言再修，或先写测试）
 └─ npm run review -- --check        # 审查包 + 门禁
 └─ 提 PR（模板四项填满）
 └─ 让 AI 以"审查者"身份读 diff + 相关模块 → 输出 🔴/🟡/💭
 └─ 逐条回应：接受 / 拒绝并写理由（拒绝理由要能被第三个人看懂）
 └─ R0 改动：放满 24h 再合并（睡一觉能发现一半问题）；R1/R2 可当天合并
 └─ 合并 → 部署 → 真机按清单点一遍
```

**AI 审查不是走过场**：让它先读 `docs/handoff.md` 的"刻意的设计与约定"和本文第 8 节黑名单，再读 diff。没有这两份上下文，它会给出"建议加 JSDoc"这类无用意见。

**作者不能给自己签字**：PR 里"审查意见"一栏必须由审查方（AI 或人）填写，作者只能回复。哪怕同一个人操作，也要分成两段、两个角色，避免"边写边觉得没问题"。

### 6.2 有第二个人碰代码时

1. `main` 设保护：禁止直推，必须 PR；
2. PR 必须过 CI `verify`；
3. 至少 1 人复核；**R0 改动要 2 人**（其中一人必须本地跑过 `npm test`）；
4. 复核人有否决权，没有"帮你改"的义务——提意见、给方案，改动由作者做。

### 6.3 紧急止血

只有线上已经坏了才允许：

1. 只做最小改动，不顺手重构；
2. 24 小时内补：审查、断言、缺陷登记、文档；
3. 止血方案若触碰红线（例如"先把权限判断注释掉"），**改为关掉功能**。关功能可接受，放权限不可。

### 6.4 发布前 10 分钟

跑 G1 → 过 E 组（页面）+ G 组（合规）+ H 组（交付）→ 真机清单逐项点 → 记一笔发布（版本、时间、改了什么）。

### 6.5 出问题之后

定级（P0/P1）→ 修 → **补一条能复现的断言** → 登记 `project-engineering-file.md` → 判断是否要把它变成门禁（能自动拦的，不要靠人记）。

## 7. 审查意见的写法

```
🔴 P0 · 云端改了，手机永远看不到
位置：cloudfunctions/admin/index.js:212 / utils/sync.js:88
现象：后台改学生只写了 updatedAt，没写 srvAt。
为什么：pull 是 `srvAt > since` 的增量拉取，没有新 srvAt 的文档永远落在游标后面，
      而且不会报错——用户只会觉得"电脑上改了手机没变"。
建议：所有 admin 写入统一走一个 helper 盖 `updatedAt + nextSrvAt()`；
      再加一条源码纪律断言：admin 里每次 update 必须出现 srvAt。
验证：tests/verify_admin.js 加一项"update 必须带 srvAt"，删掉 srvAt 会红。
```

要求：位置精确到文件:行；**为什么**要让人明白不修会怎样；建议给方向不强加实现；验证说清怎么证明修好了（能变成断言最好）；一件问题一条。

审查结束给一句总评 + 一句下一步，别只丢一堆问题。

## 8. 反模式黑名单（本项目踩过的，写新代码前先扫一眼）

| 症状 | 为什么危险 | 怎么防 |
|---|---|---|
| `catch (e) {}` 吞掉存储/网络错误 | 静默丢数据（R1） | 失败必须冒泡到界面；只允许"明确可忽略"的地方吞 |
| `oc()` 看不到已删行 | 回收站/还原遍历不到，功能形同虚设 | 需要含删除行时用 `ocAll()` |
| 软删取 `actor()` 当操作人 | `actor()` 是权限视图，可能没有 id | 取成员 id 用 `memberCurrent()` |
| `toISOString()` 取日期 | UTC 偏移，早上 8 点前算成昨天 | 统一走 `schema.ymd()`（本地时区） |
| 整批写入共用一个时间戳 | 分页边界漏数据，两端都不报错 | 每条严格递增（`nextSrvAt()`） |
| 批量操作部分失败当整体失败 | 用户重试导致重复写入 | 分开报 `saved/failed`，失败条可重试 |
| 测试用例不 `await` | 并发抢同一份内存库，红得随机 | 异步断言必须 `await` |
| `wx:key` 用了会重复的字段 | 列表错位、删错行 | 用全局唯一键（如 `kind-id`） |
| 新页签/入口没加进切换白名单 | 点了没反应 | 加完入口顺手点一次 |
| 备份只做"写"不做"读" | 出事时才发现恢复不了 | 恢复路径必须有测试真的跑过 |

## 9. 度量（每月记一次，只看趋势）

| 指标 | 当前 | 目标 |
