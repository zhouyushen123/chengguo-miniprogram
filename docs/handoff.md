### 多机构：机构号从「出厂共用」改成「一机构一号」（11-05 下午，用户要求）
- **问题**：以前 `schema.DEFAULT_ORG = 'org1'` 既是出厂值也被当真实机构号，所有客户的数据都会落进 org1 混成一团。测试期只有一个客户看不出来，第二个客户进来就是灾难。
- **现在的分工**：`org1` 只是**出厂号**（新装设备本地库的初始值，不是一个真实机构）。真实机构号是 `org_` + 10 位小写字母数字（去掉了 0/o/1/l/i 这些会看错的字符）。
- **发号在云端**：`syncv2` 的 `hello` 在「这个 openid 还没绑过机构」且「客户端带的是出厂号」时，服务端生成新号并返回 `minted:true`；带明确机构号（邀请码加入）则沿用。
- **客户端改挂**：`db.sync.reorg(newOrgId)` 把本机全部集合的 `orgId`（机构表连主键 `id` 一起）改成新号、切 `meta.orgId`、每个集合重新落盘、全量标脏。只在 `minted` 时调用——那时云端那个号下一条数据都没有，改挂不可能撞车。
- **换手机/重装不再从零开始**：空库时 `init()` 先做一次**只读**探测 `whoami`（绝不建绑定，否则会把家长绑到出厂机构上）。云端已绑定 → 记 `pendingOrg` + `openid` → pull 把数据拉回来 → 成功后才切 `meta.orgId`。拉失败本机仍是空的，不伤数据。
  - 必须一起带 `openid`：拉回数据后要靠它认出"我是成员表里的谁"，否则 actor 为空、权限过滤把数据全挡掉，看着像没恢复。
- **冲突可见化**：本机有数据、云端绑的却是另一个机构（换手机前后各建了一份）→ 不合并、停手，首页出现「这台手机的数据没和云端同步」横幅 + 说明弹窗（以前是静默停手，用户只会觉得"同事怎么看不到我录的东西"）。
- **老数据不动**：已经绑在 org1 的机构继续用 org1，一行都不用迁。org1 从此只服务那一家。
- 守卫：`verify_sync.js` 增 10 项（发号/改挂/幂等/空号/演示态/落盘/冲突停手）、`verify_invite.js` 换成「只读探测不建绑定」+「空库恢复」两项。

### 数据保护机制（11-05 晚第二批，用户："我说的是机制，数据是假的，不用迁就现有数据"）

上一轮补的是"坏了怎么救"，这一轮补的是"根本不让它坏"。三层：

**一、服务端硬约束（syncv2 `checkCore`）** —— 客户端体检是事后的，这一层才拦得住
- 机构档案不能删（删了学生和老师全成孤儿，界面上没有任何地方能还原）
- 学号在机构内唯一（排除已删除的）：家长凭学号认孩子，重号等于让家长看到别人家孩子
- 一个微信只能有一条成员关系：两条时权限按哪条生效不确定
- 一个机构只有一个负责人
- 被拒的条目随 push 响应回传 `rejected[]`，客户端落进 `meta.sync.rejects`，在「存储空间」页显示"没同步上去"；解决冲突后重新标脏自动重试。**拒绝不能静默**，否则本地看着改成功、云端永远旧值。

**二、删除是可逆的（回收站）**
- 所有软删统一走 `ctx.markRemoved`：写 `removedAt`（删除批次）+ `removedBy`（谁删的）
- 一次删除牵连的多行共用一个 `removedAt`（删学生→记录/报名；删班级→课程/报名/名单关联），还原时按「外键指向 + 同一批次」认批，**不会把上一批单独删掉的记录顺手复活**
- 删班级把"从哪些学生/成员身上摘下来"记进 `c.detached`，还原时补回去，避免还原出一个"空班"
- 删学生时家长绑定会被摘掉，还原时按「同一家长号码自动归并」的既有规则补回
- 入口：小程序「我的 → 存储空间 → 回收站」（`pages/trash`）。不提供"彻底删除"——腾空间走存储空间页，不让用户在这里做不可逆决定
- 实现要点：`oc()` 会隐藏 removed 行（界面就该藏），回收站与还原必须用新增的 `ocAll()`，否则"能删能还原"只是句空话（这条踩过一次）

**三、覆盖前留旧版（云端版本历史）**- 核心四类 `orgs / members / students / classes` 每次内容真的变化前，把旧值写进 `history` 集合（用 `sameContent` 判断，只有 `updatedAt` 变了不留历史）
- 每条约保留最近 10 版（无限归档等于把库变垃圾桶）
- `history` / `revert` 两个动作：看历史、退回某一版；回滚前也留一版当前值，滚错了能滚回来；回滚内容同样过一遍硬约束
- 权限：家长读不到历史（里面是别的孩子的档案变动）；改成员/机构只有 owner/admin
- **记录不留历史**：海量增长，留了会把库撑爆，而误改一条记录的代价远小于误改一个学生

### 云端每日全量备份（11-05 晚第三批，用户："要补"）

前面两层救的是"这台手机"和"这次误改"，这一层救的是**云数据库本身被改坏**：一次错误的批量操作、一次同步风暴、控制台误删集合，手机端拉回来的也会是坏数据。备份必须在业务数据之外、且自动跑——需要人记得点的备份等于没有。

- **新增云函数 `cloudfunctions/backup`**：`config.json` 定时器每天 03:00 跑，把每个机构的全量数据打包成 JSON 放云存储（`chengguo/backup/<机构号>/<日期>/<集合>[-n].json`，2000 条一片），清单写 `backups` 集合（一机构一天一条，同日重跑覆盖不堆副本）。保留 30 天，每次跑完顺手清过期清单与文件。
- **不塞进一条文档**：云数据库单文档 16MB，记录一多就写不进去，而这种失败发生在半夜的定时任务里，没人会发现。
- **按集合分步**：云函数 60 秒超时，整包一次稍大就会被掐断，掐断时还不知道停在哪。小程序「存储空间 → 立刻备份到云端」和电脑后台都是按集合 9 次调用、清单合并；定时器一次跑全量，超过 45 秒就存 `partial` 并在后台标「不完整」。
- **权限**：定时器/后台（无 openid）可指定机构或全量；小程序调用只认 `users` 里绑定的机构，客户端传的 orgId 一律忽略（防止改参数备份别人家）；老师可看清单，只有负责人/管理员能备份与恢复；家长连清单都看不到。
- **恢复**：按集合分次，单次上限 2000 条，返回 `nextFrom`，后台自动带上 `from` 接着写直到写完（**11-05 修复**：以前每次都从第 0 条开始切，"再点一次继续"永远回到起点，超过 2000 条永远修不到尾部）；**只写回、不删除**——恢复是用来把改坏的改成昨天那样，不是回档，顺手删掉备份之后新录的数据比不恢复更糟；写回时盖新 `updatedAt` + 递增 `srvAt`，少一个就会出现"后台说恢复了，手机还是坏的"。后台「数据安全 → 恢复到这一天」会先自动备份一份当前数据（标「恢复前」）。
- **恢复到今天会自杀的那个坑（11-05 修复）**：恢复前快照原来和每日备份共用 `orgId_date` 清单 id 与同一个目录，于是"先备份当前坏数据"这一步会把今天凌晨的好备份覆盖掉，再从这个位置恢复 → 恢复出来的是坏数据。现在快照走 `tag`（`s<时间戳36进制>`）：清单 id 是 `orgId_date_tag`、文件在 `<日期>_<tag>/` 目录，两套物理分开；同一天最多留 2 份快照，正在写的那份不会被清。
- **读失败不再当空集合（11-05 修复）**：`readAll` 原来 `.catch(() => ({data: []}))`，一次抖动就被当成"这页没数据"，整个集合备成 0 条还标 `ok`（黑名单第 1 条第三次复发）。现在读失败往上抛、重试一次、再用 `count()` 与读到的条数对账；仍失败则该集合进 `failed[]`，清单 `status: 'failed'`，后台红字提示"这份备份不全"。顺带把"清单落地"提到删旧分片之前，避免清单指向已被删掉的文件。

**修掉的两个真会丢数据的 bug**
1. `storage.readColl` 以前把"读异常"和"没有数据"混为一谈：某一片读取失败 → 当成"到头了" → 后面几百条记录静默消失，而下一次任何写入都会把这份残缺数据覆盖回磁盘，一次抖动变成永久丢失。现在 `load()` 返回 `_damage`，上层据此走恢复流程，绝不回写残缺数据。

## 2. 刻意的设计与约定（改之前先看这里）

1. **`sent` 只是本地状态，不是真实送达**。全仓零 `subscribeMessage` / 客服消息 / 短信调用。所以「已发布」目前只代表"老师这边标记完毕"，家长需自己打开小程序查看。**改文案或接推送前不要动 `sent` 的语义**（权限层 `permissions.js` 的家长可见性依赖它）。
2. **格式化字段不配麦克风**：手机号、微信号、生日、日期、邀请码——语音识别产出自然语言，填不进格式化字段。
3. **家长标识只有 `wechat` 一个字段**，学生实体没有独立家长手机号；两个都没填号码的学生不会被误判成一家人。
4. **云开关拆成两个**：`CLOUD_ENABLED`（默认 true，控 `wx.cloud.init`；`CG_CLOUD=0` 可强制关）与 `SYNC_ENABLED`（默认 false，控 `pushRecord/pull/uploadFile`）。开云 ≠ 开同步——sync 云函数模型没对齐前，记录只在本地，这是刻意的，不要为了"看上去更完整"打开它。
5. **测试编排两个坑**：
   - `verify_pages.js` 里「重启：数据持久化」用例会清 db 模块缓存重建实例，**新用例必须放在它之前**，否则页面模块拿旧快照查不到新数据；
   - 异步测试不能包进"注册时不等待"的包装函数（mock 同步 resolve 会竞态），必须纯顺序 `await`，且放文件末尾 IIFE + `process.exit(1)` 兜底。
6. **版本号断言一律引用 `schema.VERSION`**，不要再硬编码数字。
7. **真实新库不许带示例内容**：`migrate.buildFresh(stamp, {sample:false})` 是真实安装走的路，示例班级/课程只给演示数据包。想让首次体验更有内容，改首页的开通卡和向导（`pages/setup`），不要往真实库里塞假数据——用户分不清"示例"和"别人剩的"。
8. **空库判定看学生，不看班级**：`empty = 没有学生 && 没有记录`。班级可能是空壳（向导中途退出就会留下），拿它判断会把新用户误判成老用户。

## 7. 2026-11-05 晚：学科种子"只在本机、云端 0 条"的根因与修复

**现场**：V9 部署后，本机 `chengguo_v3_subjects` 有 7 条，云数据库 `subjects` 0 条，重启也不变。

**根因（两个真 bug）**

1. **维护期写入绕过了同步写钩子**。启动维护（`normalizeAll` / `ensureSubjects` / `ensureBuiltinTerm` / `repairRefs` / `repairMedia`）都是就地改数组，随后走 `core.flushAll()` 落盘 —— 而 `flushAll` 是"落盘但不算改动"的快路径，**不触发写钩子**，集合名进不了 `meta.sync.dirty`，推送永远不会带上这几张表。学科种子就是这么"消失"的：本机看得见、云端一条没有，而重启时条数没再变化，谁也不会再想起它们还没上云。
2. **`db.sync.rejects` 没在门面登记**。`utils/sync.js` 的 `pushNow` 成功后的回调读 `db.sync.rejects().length`，门面 `utils/db/index.js` 只登记了 `dirtyCols/snapshot/...`，漏了 `rejects/addRejects/clearRejects` → **每次推送成功都抛异常** → 脏集合永远清不掉 → 每次启动把整个机构重推一遍（数据没丢，但流量与耗时白烧）。

**修复**

- `maintenance.js` 新增 `markRegrown(beforeCount)`：迁移前记条数，维护后按差异对变化的集合调 `core.persist()`（走钩子 → 标脏）。`each()` 里字段被规范化时也 `persist`（条数不变，`markRegrown` 看不见）。`ensureBuiltinTerm` / `ensureSubjects` / 机构兜底 / `repairRefs` / `repairMedia` 改动后各自 `persist`。
- `meta.subjStamp`：给"已经升到 v9、种子只在本地"的设备补一次脏标记（这次修复之前升级的那批），打过戳就不再重复。
- `migrate.ensureBuiltinTerm` 的 `changed` 改成只在真新建学期/补 `termId` 时为 true（原来写成 `!!terms.find(x => x === t)`，内置学期存在时**恒为 true**，每次启动都白落一遍盘；现在维护改动会标脏，恒真就是天天重推整机构）。
- `utils/db/index.js` 门面补 `rejects` / `addRejects` / `clearRejects`。
- `tests/verify_datamodel.js` 新增 G 组 3 项：v9 设备丢种子→标脏、v8 升级→新表标脏、推完清脏后第二次启动不再标脏。

**基线**：25 套件 / **542 项**断言全绿。

**部署**：本轮只改小程序端，云函数不用重传（但上一轮的 `syncv2` / `backup` / `admin` 仍需部署 + backup 触发器/超时 60s）。

### 新增：引用完整性体检 / 自愈（`utils/db/integrity.js`）

以前只有 `repairRefs()`（补记录的 cid/tid/courseId），V10 多了 `class_courses` 这张纯关系表，
却没有对应的守卫。现在：

- `integrity()`（只读）→ 问题清单，覆盖：绑定指向不存在的班/课、绑定指向墓碑、同班同课重复绑定、
  记录的 cid/sid/courseId 悬空、学生/成员范围里的悬空 id、课时账悬空、软删行缺 `removedAt`、
  缺 `orgId`、跨机构残留、集合内 id 重复。
- `repairLinks()`（自愈）→ 启动时跑一次（`maintenance.init` 与 `restoreSnapshot` 都接）。
- 门面：`db.integrity()` / `db.repairLinks()`。

**自愈口径（重要，别再"见悬空就删"）**：只修「本地已有这一行且是墓碑（removed / mergedInto）」的引用，
**整行不存在的一律只报不修**。原因：新设备上云时拉取按集合分批，可能先到 students 后到 classes，
这时学生身上的 clsIds 在本机看着就是悬空的；启动就修 → 推回云端 → 等于用一次本地修复把全班名单清空。

### 同批修掉的四个真问题

| 问题 | 后果 | 修法 |
|---|---|---|
| `syncmerge.pickWinner` 同时间戳一律取远端（含墓碑） | 另一台设备同毫秒删掉、本机也改过 → 记录静默消失（11-05 数据消失的同类口子） | 同时间戳时**活着的赢**；更晚的删除仍然生效 |
| `sync.applyRemote` 不看 `setColl` 返回值 | 内存改了、磁盘没写，游标照样推进 → 这批文档永不重拉，重启即丢 | 落盘失败返回 `ok:false`，`pullNow` 报错且不推进游标 |
| `records.save` 直接采信传入的 `courseId` | 页面停在旧数据上（课程刚被合并/删）→ 记录挂到空课程，统计漏条 | 验活，失效则按课程名重认，再不行清零 |
| `records.attachCloud` 只凭 rid 改照片 | 后台补传照片可跨范围写别人的记录 | 落库前 `canSeeRecord` 兜一次 |

### 界面上是什么样

存储空间页的「数据体检」卡现在**分两层**（不是两张卡：做成两张会让用户以为是两个地方要分别看）：

| 层 | 看什么 | 修什么 |
|---|---|---|
| 记录层（原有 `audit.scan`） | 人/班/机构本身是否对得上、学号是否重复缺失 | 「修复可自动处理的问题」 |

头部一句话是**两层综合**的（`syncHead`）：`N 处需要处理` / `正常（N 处待同步）` / `一切正常`。
只按 audit 判断会出现"右上角一切正常、下面却列着断线"的自相矛盾，所以加了 `headHint`。

### 关键设计：把「待同步」和「故障」分成两种颜色

`integrity()` 的每条结果多了 `wait` 字段——**整行不存在** = 可能是还没被同步下来。

这个区分不是为了好看，是为了**不让用户点错按钮**：如果统一显示成红字，用户会不断点「修复断线」，
而修复对这类故意不动（见 §19 的口径），点了没反应会以为功能坏了。

所以：
- `binding.cls` / `binding.course` / `record.sid` / `enroll.stu` 等"整行不存在" → `wait: true`，灰字 +「待同步」
- `binding.courseDead` / `binding.clsDead` / `binding.dup` / 记录指针失效 / 范围悬空 → 红字
- 判定写在 `integrity()` 里（`!cls[id]` 即 wait），页面只负责上色

分组名是中文，映射表在 `integrity.js` 的 `KIND_LABEL`——**不放在页面**，
因为 kind 由数据层定义，以后加一类检查要能自动出现在界面上，不能靠人去改页面。

### 接口

- `db.integrityGroups()` → `[{ kind, label, count, wait }]`，按「故障优先、条数降序」排
- 页面：`refreshLinks()` / `syncHead()` / `fixLinks()`
- 同步完成后三层一起刷新（`refreshAudit + refreshLinks + syncHead`）——
