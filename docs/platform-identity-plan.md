# 平台身份基座方案（数据平台型 · 业务机构型）

> 状态：**方案待拍板，未改任何代码。**
> 提出：2026-11-08 10:30。用户原话要点：
> 「先不做这些功能，但是要预留好基座，把数据字段做成平台通用的，业务上还是单个机构展示；
> 但在家长端要更方便——一个孩子在 A、B、C 机构，都要能看到他们的成果。」
> 本文是后续实施的唯一依据，实施前不改代码。

---

## 1. 一句话

**字段按平台配，业务按机构走，家长按孩子看。**

- 数据层：每个「人」有平台级标识，机构只是他的一个关系。
- 业务层：老师端、班级、课程、记录，全部照旧锁在单机构内，互相不可见。
- 展示层：只有**家长端**做跨机构聚合，且聚合的是「他自己孩子」。

---

## 2. 三条铁律（越界即出事，代码里必须守）

| # | 铁律 | 原因 |
|---|---|---|
| R1 | **老师端永不跨机构**，连"这孩子还在别处上课"的提示都不给 | 一旦可见就是泄露机构生源，第一家机构立刻不信任你 |
| R2 | **平台永不自动归并**，合不合由家长确认 | 双胞胎 / 同名 / 代管亲戚孩子，自动合并会把两个孩子的成绩混给一个人看 |
| R3 | **不对机构招商、不自称平台、不做跨机构排名** | 一旦如此，性质从"工具"变成"平台经营者"，备案与主体责任整套换 |

补充一条**合规红线**：阶段 2 上线跨机构聚合，属于处理目的变更，隐私政策必须改、**家长需重新同意一次**。预留字段本身不需要，开功能需要。

## 4. 数据模型：三层

```
平台主体层    platform_person        pid（平台唯一）— 只在阶段 2 才真正落表
                 ↑ pid
机构关系层    students               orgId + pid  ← 一个孩子在某机构的那份档案
                 ↑ studentIds
监护人层      members                openid + orgId  ← 同一微信可在多机构各有一条
```

- **不是**把 `students` 提到平台层。学生档案依然**一机构一份**，各自持有成绩、评语、照片。
- `pid` 的作用只有一个：**认出"这两份是同一个人"**。它不承载任何成绩，所以不构成跨机构数据汇聚。
- 家长账号（`openid`）本来就是平台级的，不需要新建——阶段 1 已证明 `members` 支持一人多机构。

## 5. 字段设计（阶段 0 全部预留，业务一句不读）

### 5.1 新增字段

| 表 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 全部实体（经 `audit()`） | `pid` | string，空串表示未分配 | 平台主体标识；只有 `students` / `members` 会真正赋值，其余表留空 |
| `students` | `pid` | string | 这个孩子在这份档案里的平台主体 id |
| `students` | `pidSrc` | `'auto' \| 'confirmed'` | `auto`=建档时自动生成；`confirmed`=家长确认过与另一份档案是同一人 |
| `members` | `pid` | string | 监护人平台标识（同一微信跨机构一致） |
| 本机 `meta` | `schemaVer` | number | 库结构版本，为将来迁移留钩子 |
| 本机 `meta` | `pidVer` | number | 补号批次，避免重复补 |

### 5.2 `pid` 生成规则

```
pid = 'p' + 34 位时间戳转 36 进制 + 4 位随机 + 4 位序号
例：p m3k9x2a7 bq7f 0001
```

- 用 36 进制压缩长度，肉眼可读、可截断显示后 6 位给人工核对。
- **不用裸 `Date.now()`**：多设备并发会撞号；必须叠加随机位。
- **不做确定性哈希**：阶段 0 没有任何代码读 `pid`，两端短暂不一致无害；同步是整条覆盖 + `srvAt` 后写优先（LWW），最终会收敛到同一个值。
  > 若阶段 2 出现"离线也要推出同一个 pid"的诉求，再给 `orgs` 表加 `pk`（机构平台密钥），用 `pid = 'p' + org.pk + id.toString(36)` 改成确定性生成。**阶段 0 不做**，避免过早引入机构密钥分发问题。

### 5.3 补号（老数据）

```js
// 幂等：已有 pid 原样保留；只给空值补
function backfillPid() { /* 遍历 students / members，空则生成 */ }
```

- 在 `db.init()` 之后跑一次，`meta.pidVer` 记录已跑过，不重复。
- 两台设备各自补会补出不同 pid（无害，LWW 收敛）；机构只有一台设备时就是权威值。

## 6. 分阶段实施

### 阶段 0 · 字段预留（**本轮要做，约 1~2 小时**）

改 4 处 + 1 个守卫，**业务代码零改动、界面零变化、云函数不用动**：

1. `utils/db/schema-base.js` → `audit()` 返回里加 `pid`（默认 `''`）
2. `utils/db/schema.js` → `normalizeStudent` 加 `pid, pidSrc`；`normalizeMember` 加 `pid`
3. `utils/db/core.js` → 新增 `newPid()`；`utils/db/index.js` 暴露
4. `utils/db/students.js` / `members` 建档时赋 `pid = newPid()`（一行）
5. `tests/verify_platform_base.js`：`pid` 只在建档生成、不参与任何权限/业务判断、老数据补齐幂等、不写到不相关表

验收：数据体检结果不变、同步后字段完整、老数据都有 pid。

### 阶段 1 · 允许一个微信进多家机构（**真需要第二个机构时**）

- 云端 `finishJoin`：`ORG_BOUND` 改为"允许新建第二条成员关系"，`users` 表由"一 openid 一条"改为"一 openid 一条成员索引"（`orgIds: []`）。
- 客户端：`meta.orgId` 仍单值，新增**机构切换器**——只在"我的机构 > 1"时出现。
- 切换语义：换 `orgId` → 清本机业务表 → 按新机构重拉。**这会清掉草稿**，所以切换前必须给明确提示。
- 老师端体验不变（99% 的老师只有一个机构，切换器根本不出现）。

> 这一阶段的代价主要不在代码，在**用户心智**："切换机构会重新加载"。所以只在真有需求时做。

### 阶段 2 · 家长端按孩子聚合（**核心价值所在**）

**架构判断：老师端继续走本地镜像，家长端改成云端直查。**

| | 老师端 | 家长端 |
|---|---|---|
| 数据来源 | 本机镜像（需离线录入） | 云端直查（纯只读） |
| 跨机构 | 永远不要 | 必须支持 |
| 为什么 | 上课没网也要能录 | 只读，没必要离线；直查就不用在本机同时装两家库、不用切机构清库 |

这一分离是整个方案的关键：**多机构问题被关在家长端里，老师端一行不动。**

新增 2 个云端只读接口（放 `family` 云函数，与已读/留言同源，鉴权逻辑一致）：

```
familyKids          → 我所有的孩子（按 OPENID 反查所有机构的 members）
  out: kids[{ pid, name, photo, orgCount,
              orgs[{ orgId, orgName, color }],
              lastRec{ date, course, score, tag } }]

familyKidRecords    → 某个孩子的成果时间线（跨机构混排）
  in : pid, limit, cursor, orgId?(筛选)
  out: list[{ rid, orgId, orgName, date, course, score, tag, note,
              photos, audio, viewed, myNotes }]
```

鉴权（fail-closed，与 `fbView/fbNote` 同一套）：

1. `OPENID` → 查 `members`（**所有机构**，不只一个）→ 得到每个机构的 `studentIds`
2. 按 `studentIds` 取 `students` 行 → 按 `pid` 匹配
3. 只返回 `sent === true` 的记录（未发布的一律不给）
4. 只返回**自己孩子**；别人的 pid 直接 `FORBIDDEN`，不区分"不存在"和"无权"

**家长确认合并**（`familyLink`）：

```
in : pidA, pidB, confirm: true
逻辑：校验两个 pid 都在当前 OPENID 的成员范围内 → 统一为较早的那个 pid
     → 两条 students 行写 pidSrc='confirmed'
不移动任何记录、不合并数据，只让它们"认出是同一人"
```

家长在第二家机构绑孩子时，若同微信已绑过**同名**孩子 → 弹「张小明 也在这家上课吗？」，是→关联，否→建独立档案。

家长端界面（`pages/index` 已有 chips 骨架）：

- 孩子卡片：`张小明 · 2 家机构 · 5 次课` + 机构色点
- 时间线：倒序混排，每条挂机构标签
- 顶部：`全部 / 机构 A / 机构 B` 筛选
- 点进 `pages/student`：同样混排，档案基础信息显示一份，各机构"在读班级/课程"分区列

### 阶段 3 · 可选增强

- 手机号一键认领（复用 F-04 的 `parentPhone`，需小程序主体已认证）
- 跨机构转学：家长确认后把档案"带走"，原机构只留历史只读
- 孩子升学/换机构的历史时间线导出

## 7. 明确不做（写清以免越做越大）

- ❌ 平台级独立 `students` 表（阶段 2 前不建，`pid` 只是字段）
- ❌ 老师端跨机构视图、跨机构学生搜索
- ❌ 自动合并、相似度归并、手机号自动匹配
- ❌ 跨机构成绩对比 / 排名 / 成长曲线对齐（会触及"平台评价学生"的责任）
- ❌ 机构自助注册、公开招商页
- ❌ 家长搜索其他孩子（连模糊搜索都不给）

## 8. 迁移与回滚

| 阶段 | 迁移 | 回滚 |
|---|---|---|
| 0 | `backfillPid()` 一次性补号，`pidVer` 防重复 | `audit()` 去掉 `pid` + normalize 去掉声明即可，老数据字段留着无害（会被裁掉） |
| 1 | 无（`users` 表兼容 `orgIds` 单元素） | 恢复 `ORG_BOUND`，把第二机构成员的 `status` 置 `disabled` |
| 2 | 家长确认时写 `pid` 关联，不做批量回填 | 隐藏家长端聚合入口（`famOn` 开关），回落本机构 `kids` |

**每阶段都有独立开关，出问题不影响已发布记录与已加入家长。**

## 9. 验收

**阶段 0**
- 数据体检（`integrityGroups`）结果与改动前一致
- 新建学生/成员有 `pid`；老数据在启动后自动补上；重复启动不重复补
- 两机同步后 `pid` 一致
- 老师端、家长端、发布流程**肉眼无任何变化**

**阶段 2**（真机）
- 家长同一个微信在 A、B 两家机构各绑一个孩子
- 若两个档案确认关联 → 家长端看到 1 个孩子、时间线混排、2 个机构标签
- A 机构老师进管理页 → 看不到 B 的任何信息、看不到"还在 B 上课"
- 用另一个微信的 pid 请求 `familyKidRecords` → 被拒

## 10. 成本与风险

| 项 | 评估 |
|---|---|
| 阶段 0 成本 | 4 个文件 + 1 个守卫，**约 1~2 小时**，无部署、无界面变化 |
| 阶段 2 成本 | 2 个云端接口 + 家长端 2 个页面改数据源 + 机构标签，中等；需重部署 `family` |
| 最大风险 | **不是技术，是把两个孩子的数据混给一个家长**。所有设计围绕"必须家长确认" |
| 合规风险 | 阶段 0 零增量；阶段 2 需改隐私政策 + 重新取得同意 |
| 数据风险 | `normalize*` 裁字段是最易漏的点，守卫必须钉死 |

---

## 11. 建议

**现在只做阶段 0。** 理由：

1. 成本几乎为零，但把将来最贵的"数据迁移"提前消化掉。
2. 业务与界面完全不变，不影响正在做的邀请卡 / 家长反馈。
3. 真到有第二家机构时，阶段 1、2 才需要决策——那时你有真实用户数据支撑，而不是现在猜。

阶段 0 做完后，等**第一个真实的多机构家长出现**，再启动阶段 1+2。
