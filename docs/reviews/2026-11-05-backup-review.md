## 总评

机制层面做得对：备份放云存储而不是塞进一条文档、按集合分步避开 60 秒超时、恢复只写回不删除、清单落库可追溯、23 项断言里真的跑了一遍恢复。**这些决定都对，注释也写出了"为什么"，这是好代码的样子。**

但恢复链路有 3 个必然会咬人的问题，我用测试桩**实际复现**了（不是"看起来有问题"）；另有 1 个是结构性问题、按触发条件降为 P1（见文末「复核」）：

| # | 级别 | 问题 | 后果 |
|---|---|---|---|
| 1 | 🔴 | 恢复前的 safety 备份覆盖当天正常备份 | 恢复出来的是坏数据，且好备份永久丢失 |
| 2 | 🔴 | 单集合超过 2000 条后，点多少次都只恢复前 2000 条 | "再点一次继续"是假的，尾部永远修不回来 |
| 3 | 🔴 | 读云端某一页失败被当成"这一页没有数据" | 整个集合备成 0 条，清单标 `ok` |
| 4 | 🟡 | 定时器把所有机构跑在一次调用里，共用 60 秒 | 机构一多，后面的机构当天没有任何备份，且无告警 |

结论：**备份能生成，但"出事时能不能恢复回来"这条链现在是断的。** 前 3 条按 v2.0 判定四问第 3 问（"恢复一次备份之后数据还在吗"）都是 P0；第 4 条取决于机构数量，降为 P1。

## 🔴 P0-1 · 恢复到"今天"会先把今天的好备份覆盖掉

**位置**：`cloudfunctions/backup/index.js:110-113`（`prev` 复用同日清单）、`:129`（`lib.pathOf` 同日同路径）、`cloudfunctions/admin/public/index.html:764`（恢复前自动跑 safety 备份）

**现象**（复现结果）：
```
备份里学生叫：小明（好数据）
safety 备份后同一路径的文件：小明（被改坏）   ← 好备份被覆盖
恢复结果：ok, written=1
恢复后云端学生叫：小明（被改坏）             ← 恢复出来的是坏数据
```

**为什么**：清单 id 是 `orgId_date`、文件路径是 `<orgId>/<date>/<coll>.json`，所以"同一天"只有一份备份。而后台"恢复到这一天"的第一步是拿**当前（可能是坏的）数据**再备一次——它写的正是今天那个位置。于是：
- 凌晨 3 点那份好备份被中午的坏数据覆盖；
- 接着 "恢复到今天" 读到的就是坏数据。

这不是边角情况：**"今天凌晨还好，中午被改坏，恢复回来"正是这个功能最主要的用法。**

**建议**：safety 备份用独立命名空间，别碰正常备份。
- `manifestId(orgId, date, tag)` / `pathOf(orgId, date, tag, coll, part)`，safety 传唯一 tag（如 `s` + `HHmm`）；
- 清单加 `kind: 'safety'`，`prune` 对 safety 只留最近 2 份（注意 `lib.expired()` 现在按 `date` 算天数，带后缀的日期会 `isNaN` 而永不清理——改时要一起处理）；
- 后台列表里把 safety 单独分组，别和"每日备份"混在一列。

**验证**：加一条断言——"今天已备好 A 版本 → 数据改成 B → 跑 safety 备份 → 用今天的日期恢复 → 还原出 A"。这条断言在现在的代码上是红的。

## 🔴 P0-2 · 记录过 2000 条，恢复永远走不到尾部

**位置**：`cloudfunctions/backup/index.js:225`（`docs.slice(0, RESTORE_CAP)`）、`:236`（返回 `skipped`）、`cloudfunctions/admin/public/index.html:777-779`（提示"再点一次继续"）

**现象**（复现结果，2100 条记录）：
```
第一次：written=2000 skipped=100
第二次：written=2000 skipped=100（没有前进）
前 2000 条修好 2000 条；2001~2100 仍是坏的 100 条
```

**为什么**：每次恢复都从 `docs[0]` 开始切 2000 条，没有 offset 也没有"写完了哪一段"的记录。所以第二次点击覆盖的是同一批 2000 条，`skipped` 永远是 100，UI 却告诉用户"再点一次继续"。**用户会点十次，然后以为恢复了。**

**建议**：让恢复可续。
- 入口参数加 `from`（本集合内偏移），`restoreColl` 返回 `nextFrom`；
- 后台拿到 `nextFrom` 就自动继续下一次调用，直到 `skipped === 0`（人可以不用管，一次点击跑完）；
- 或者更省事：`restoreColl` 内部按时间预算循环（`while (now() - t0 < 40s)`），自己把集合写完，超时才返回 `nextFrom`。

**验证**：现有断言 `tests/verify_cloudbackup.js:418` 只断言了 `skipped === 100`——**它把这个 bug 当成了正确行为**。改成"再调用一次后 `skipped === 0`，且第 2100 条的字段已被修复"。

## 🔴 P0-3 · 读失败 = 空集合，备份变短但清单标 `ok`

**位置**：`cloudfunctions/backup/index.js:44`（`.get().catch(() => ({ data: [] }))`）、`:61`（`allOrgs` 同款）

**现象**（复现结果，云端 250 条学生）：
```
云端实际 250 条，备份记了 0 条
清单状态：ok（ok 表示"完整"）
```

**为什么**：这是本项目已经踩过、并且写进黑名单第一行的那个坑——`readColl` 把"读异常"当成"没有数据"。它在这里更隐蔽：
- 单页失败 → `rows.length < PAGE` → 直接 `break` → 返回半截数据；
- 全页失败 → 该集合 0 条，其他集合正常 → `status` 仍然是 `ok`；
- 30 天后 `prune` 照常删掉旧的好备份，坏的这份顶上去。**等你发现时，一个月的备份都是短的。**

**建议**：
- `readAll` 不吞异常：失败就抛，让 `runOrg` 把该集合标成 `status: 'failed'` 并写进 `missing`（现在 `missing` 只表达"没跑到"，不表达"跑失败了"）；
- 顺手把 `counts` 与云端 `count()` 对数：不一致就标 `suspect`，别让 `ok` 这么廉价；
- `allOrgs` 同理——机构列表读失败会退化成"没有机构需要备份"，返回 `NO_ORG`，看着像正常。

**验证**：加一条断言"读某一页抛错 → 清单 `status !== 'ok'`，且 `missing` 里列出来"。现在这条会红。

## 🟡 P1 · 所有机构跑在一次调用里，机构和数据一多，后面的机构当天没有备份

**位置**：`cloudfunctions/backup/index.js:274-281`（`for (const orgId of orgs)` 无总体预算判断）、`:28`（`TIME_BUDGET` 各机构各自从 0 起算）

**为什么**：定时器是"一次调用遍历所有机构"，外层循环没有任何总预算，而云函数整体只有 60 秒。单机构耗时大致是"9 个集合的读+上传"，小机构几秒、大机构十几秒，**机构数 × 单机构耗时一旦超过 60 秒，排在后面的机构就被硬杀**：没有清单、`prune` 没跑、定时任务的返回值也没人看。

（先前这版把它写成"第二个客户上线即必然空备份"，夸大了——小机构两个也能跑完。真实触发条件是"机构数或单机构数据量变大"，所以按 P1 处理；但**静默**这一点必须修。）

**建议**：一次调用只处理一个机构。定时器里先 `allOrgs()`，然后逐个 `cloud.callFunction({name:'backup', data:{orgId}})`（云函数自调用），每个机构各自 60 秒；或用 `orgCursor` 接力。另外给"昨天没有备份的机构"一个显式告警位——后台概览显示"未备份机构数"，让漏备不再无声。

**验证**：断言"三个机构、每个机构故意跑满 20 秒 → 三个都有清单"（用假时钟推进 `Date.now` 即可，不需要真等）。

## 🟡 P1 · 备份集合清单缺 `users`，而它正是"能不能找回数据"的钥匙

**位置**：`cloudfunctions/backup/lib.js:14`（`COLLS` 里没有 `users`）、`:50`（`PRIVATE` 剥掉 `_openid`）

**为什么**：`users` 存的是 `openid → orgId` 绑定。云库被清空、只恢复业务集合之后，每台手机打开时 `whoami` 都会说"未绑定"。**有本机数据的手机能自愈**：`utils/sync.js:64` 会拿本机 `meta.orgId`（真实机构号）去 `hello`，服务端 `minted` 只对出厂号 `org1` 成立，于是直接把 `users` 重新绑回原机构（`syncv2/index.js:160-169`）——这条路走得通，但**没有任何文档写过它，也没断言盯着**。

真正会掉下去的是**清过缓存 / 换新手机**的人：本地是空库 → 走 `whoami` → 未绑定 → 直接 `skipped`（不会乱发号，这点是对的），结果是他再也回不到原机构，只能找负责人重新发邀请码；而邀请码在 `invites` 集合里，同样不在备份清单里。

顺带一个实现障碍：`cleanDoc` 会剥掉 `_openid`，所以**就算把 `users` 加进 `COLLS` 也备不出可用的东西**，得单独处理（备份时保留 `_openid`，恢复时用 `add({data:{_openid,...}})`）。

**建议**：把 `users` 作为第三类对象单独备（清单里标 `kind: 'bindings'`），恢复时单独一步；至少在 `docs/handoff.md` 写明"库被清空后的恢复顺序：恢复业务集合 → 各手机打开一次重建 users → 再核对 members"。

**验证**：一条断言"清空 users 后按文档顺序恢复，whoami 能重新返回原 orgId"。

## 🟡 P1 · 失败没有重试，`failed > 0` 在 UI 上等于成功

**位置**：`cloudfunctions/backup/index.js:232`（单条写入失败只 `return 0`）、`cloudfunctions/admin/public/index.html:773-781`（只看 `ok`/`skipped`，不看 `failed`）

**为什么**：`CONC=10` 并发写，CloudBase 偶发限流就会失败几条。恢复返回 `failed: 3`，后台当成功继续下一步，最后 toast "恢复完成"。用户拿到的是一份**少了 3 条、没人提**的数据。

**建议**：单条失败重试一次；`failed > 0` 时后台必须红字报出来（"3 条没写回，再点一次"），别并进成功路径。

## ~~🟡 P1 · CI 的 `paths-ignore` 会与"PR 必须过 verify"死锁~~（**复核后撤回：审错了**）

**原意见**：`.github/workflows/deploy.yml` 的 `paths-ignore`（`**.md` / `.github/**` / `tests/**`）会让只改文档/测试/CI 的 PR 不触发 `verify`，若 main 开了"必须过 verify"的保护就永远合不进去。

## 🟡 P2 · `npm run review` 会把已暂存的改动算两遍

**位置**：`tools/review.js:64`（`statCmds` 同时含 `diff --numstat HEAD` 与 `diff --numstat --cached`）

**为什么**：`git diff HEAD` 已经包含已暂存改动，再叠一次 `--cached` 就重复计数。后果是"断言只增不减"这条提示会误报：暂存了测试改动后跑 review，删除行被算成两倍，于是提示"这次测试文件的删除行多于新增行"。

**建议**：`diff --numstat HEAD` 与 `diff --numstat --cached` 二选一（前者覆盖后者），或改成 `git diff --numstat HEAD -- .` 加 `git diff --numstat`（未暂存）。
